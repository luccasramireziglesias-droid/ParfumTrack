🆕 Vulnerabilidades detectadas y corregidas en v6
V6-01 sendOtpEmail() fire-and-forget — Worker termina antes de enviar el correo Corregido
Severidad
Alto
Impacto
El OTP se generaba y almacenaba en KV correctamente, pero el correo nunca llegaba al usuario. El runtime de Cloudflare Workers termina tan pronto como el handler retorna una Response — cualquier Promise pendiente es cancelada. La llamada a Brevo API (8 s timeout) era ignorada silenciosamente.
Causa
sendOtpEmail() se llamaba sin await. El Worker retornaba { sent: true } antes de que la solicitud HTTP a Brevo siquiera se enviara.
Cómo reproducir
Solicitar un OTP, verificar en los logs del Worker: no hay ningún registro de Brevo. La respuesta es siempre { sent: true } incluso con API key inválida.
Solución
Agregar await antes de la llamada y capturar errores con .catch() para que fallen silenciosamente sin romper el flujo.
// ANTES (vulnerable — fire-and-forget)
sendOtpEmail(emailLower, otp, env).catch(e =>
  console.error("[trial] email error:", e?.message)
);

// DESPUÉS (corregido — awaited)
await sendOtpEmail(emailLower, otp, env).catch(e =>
  console.error("[trial] email error:", e?.message)
);
Estado
✓ Corregido — functions/trial.js
V6-02 FROM_EMAIL con dirección no verificada en Brevo — error 401 en envío Corregido
Severidad
Alto
Impacto
Brevo rechaza envíos desde remitentes no verificados con HTTP 401 "Key not found" o similar. Combinado con V6-01 (fire-and-forget), este error ni siquiera aparecía en logs — el sistema de OTP era completamente no funcional en producción.
Causa
FROM_EMAIL estaba configurado como parfumtrack@gmail.com en wrangler.jsonc — dirección nunca verificada en la cuenta Brevo. La única dirección verificada en Brevo era luccasramireziglesias@gmail.com.
Causa secundaria
La BREVO_API_KEY que circuló durante la sesión de debugging era antigua e inválida (revocada). La clave fue regenerada y actualizada como GitHub Secret.
Solución
Cambiar FROM_EMAIL en wrangler.jsonc a la dirección verificada. Regenerar y rotar la API key de Brevo.
// wrangler.jsonc — ANTES
"vars": {
  "FROM_EMAIL": "parfumtrack@gmail.com",
  "FROM_NAME":  "Parfum Track"
}

// wrangler.jsonc — DESPUÉS
"vars": {
  "FROM_EMAIL": "luccasramireziglesias@gmail.com",
  "FROM_NAME":  "Parfum Track"
}
Estado
✓ Corregido — wrangler.jsonc + nueva API key
Nota
BREVO_API_KEY nunca fue ni será commiteada al repositorio. Se sube exclusivamente vía wrangler secret put desde el CI.
V6-03 .git/ y .wrangler/ expuestos como assets estáticos públicos Corregido
Severidad
Alto
Impacto
Wrangler assets estaba configurado con directory: "." (raíz del proyecto) y sin lista de exclusión. El directorio .git/ contiene todo el historial del repositorio (código fuente, mensajes de commit, archivos borrados). .wrangler/ puede contener tokens de sesión locales. Ambos serían accesibles vía GET /.git/config, GET /.git/HEAD, etc.
Causa
Ausencia del archivo .assetsignore — Wrangler lo respeta igual que .gitignore para filtrar qué archivos subir como assets estáticos.
Cómo reproducir
Sin el fix: curl https://parfumtrack.pages.dev/.git/config devolvería el archivo de configuración Git con la URL del repositorio remoto y ramas.
Solución
Crear .assetsignore en la raíz del proyecto con exclusiones explícitas.

V6-05 CI/CD pipeline completamente roto — 3 errores concatenados Corregido
Severidad
Alto
Impacto
Ningún push a main resultaba en un deploy exitoso. El producto tenía un pipeline CI/CD configurado pero no funcional desde el inicio. Cualquier fix de seguridad commiteado no llegaba a producción.
Error 1
wrangler deploy sin --config wrangler.jsonc — Wrangler buscaba wrangler.toml por defecto y no encontraba el entry point.
Error 2
El bloque de wrangler secret put usaba --name parfumtrack como argumento posicional, pero la sintaxis correcta es --name en modo legacy. El Worker no recibía las secrets BREVO_API_KEY ni LICENSE_SERVER_SECRET.
Error 3
CLOUDFLARE_API_TOKEN y CLOUDFLARE_ACCOUNT_ID no estaban configurados como GitHub Secrets — el workflow los referenciaba pero estaban vacíos.
Solución
Tres fixes en .github/workflows/deploy.yml + usuario agregó los secrets en GitHub.
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Wrangler
        run: npm install --global wrangler@3.90.0

      # Fix 2: wrangler secret put con sintaxis correcta
      - name: Set Worker secrets
        run: |
          [ -n "$BREVO_API_KEY" ] && printf '%s' "$BREVO_API_KEY" | \
            wrangler secret put BREVO_API_KEY --name parfumtrack || true
          [ -n "$LICENSE_SERVER_SECRET" ] && printf '%s' "$LICENSE_SERVER_SECRET" | \
            wrangler secret put LICENSE_SERVER_SECRET --name parfumtrack || true
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          BREVO_API_KEY: ${{ secrets.BREVO_API_KEY }}
          LICENSE_SERVER_SECRET: ${{ secrets.LICENSE_SERVER_SECRET }}

      # Fix 1: --config wrangler.jsonc
      - name: Deploy
        uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          command: deploy --config wrangler.jsonc
Estado
✓ Pipeline verde — deploy.yml corregido
V6-06 Rate limit de OTP demasiado restrictivo — 3/hr bloqueaba usuarios legítimos Corregido
Severidad
Medio
Impacto
Un usuario que cometía un typo en su email, o que solicitaba reenvío del OTP (porque tardó más de 10 minutos), quedaba bloqueado tras 3 intentos en 1 hora. La experiencia de onboarding se rompía para usuarios legítimos — imposibilidad de activar el trial.
Causa
El límite de 3 requests/hr por IP y por email era demasiado bajo para el flujo real: el usuario puede necesitar 2-3 intentos solo para entrar el email correcto más un reenvío.
Solución
Elevar a 10/hr — suficiente para uso legítimo, aún efectivo contra automatización.
// ANTES
const rlIp    = await checkRateLimit(env, `rl_otp_ip_${ipHash}`,    3, 3600);
const rlEmail = await checkRateLimit(env, `rl_otp_em_${emailHash}`, 3, 3600);

// DESPUÉS
const rlIp    = await checkRateLimit(env, `rl_otp_ip_${ipHash}`,    10, 3600);
const rlEmail = await checkRateLimit(env, `rl_otp_em_${emailHash}`, 10, 3600);
Estado
✓ Corregido — functions/trial.js
Nota
El rate limit de verificación (5 intentos por OTP, 5/15min por email) permanece sin cambios — es el control crítico contra brute-force del código de 6 dígitos.
🔄 Auditoría del nuevo módulo Auto-Sync (/sync)
SYN Endpoint /sync — Análisis de seguridad completo Aprobado

El módulo functions/sync.js implementa sincronización automática de datos atada a email verificado. Análisis completo de los controles de seguridad:

ControlImplementaciónEstado
Autenticación HMAC-SHA256(syncCode, LICENSE_SERVER_SECRET) — mismo mecanismo que /backup; timingSafeEqual() para comparación ✓ Correcto
Origen del token syncCode = SHA-256(email)[:32] emitido por /trial tras OTP verificado; syncToken = HMAC(syncCode) — no puede ser forjado sin LICENSE_SERVER_SECRET ✓ Correcto
Rate limiting 120 saves/hr por IP + 120 saves/hr por código; 60 loads/hr por IP. Ventana deslizante vía KV con TTL automático ✓ Correcto
Límite de tamaño Payload > 5 MB rechazado con HTTP 413 antes de intentar escribir en R2 ✓ Correcto
Aislamiento por usuario R2 key: sync/{emailHash} — cada usuario solo puede acceder a su propio slot; el hash previene enumeración ✓ Correcto
Validación de token format /^[0-9a-f]{64}$/.test(token) — rechaza tokens malformados antes de la operación criptográfica ✓ Correcto
CORS Allowlist idéntica a otros endpoints: parfumtrack.pages.dev + parfumtrack.workers.dev + localhost ✓ Correcto
Service Worker /sync excluido del cache en sw.js — siempre va a red ✓ Correcto
Orden de rate limit Rate limit por IP ocurre antes de verificar el token HMAC — mitiga DoS dirigido a la operación criptográfica ✓ Correcto

Hallazgo: el rate limit de POST tiene doble verificación (IP y código) pero el segundo checkRateLimit ocurre después de verifyToken(). Esto significa que un atacante con token válido podría enumerar si el doble rate limit es distinto, aunque en la práctica el límite de 120/hr por código es suficientemente generoso para uso legítimo. Riesgo: despreciable.

SYN-RR syncCode y syncToken almacenados en localStorage — accesibles por XSS Aceptado
Severidad
Medio
Descripción
Las claves pt_sync_code y pt_sync_token se guardan en localStorage. Un ataque XSS exitoso podría exfiltrar estas credenciales y leer/sobreescribir los datos de sincronización del usuario en la nube.
Impacto real
Bajo-Medio — requiere un XSS activo, que ya está mitigado por escapeHTML() en todos los puntos de render y CSP sin unsafe-eval. No hay datos financieros críticos en sync — son los mismos datos que el usuario tiene en localStorage de todas formas.
Alternativa
Almacenar en sessionStorage (se pierde al cerrar pestaña — obliga a re-autenticarse) o en una cookie HttpOnly (requiere cambio de arquitectura — el token lo emite el Worker, no el servidor de páginas). Ambas opciones tienen tradeoffs de UX significativos.
Motivo aceptación
La superficie XSS primaria está cerrada. El riesgo residual es inferior al costo de UX de perder la sesión de sync al recargar la página.

OBS-01 Log de debugging revela longitud de BREVO_API_KEY en Workers logs Bajo riesgo
Severidad
Bajo
Descripción
La línea de debug console.log(`[trial] Calling Brevo API, ..., key length: ${apiKey.length}`) fue agregada para diagnosticar el problema de envío. Revela la longitud de la API key a cualquier persona con acceso a los Workers Logs en el dashboard de Cloudflare.

// Línea de debug temporal — remover una vez verificado el funcionamiento
console.log(

OBS-02 Claves KV de rate limiting se acumulan sin limpieza explícita Bajo riesgo
Severidad
Bajo
Descripción
Las claves de rate limiting siguen el patrón {prefix}_{windowTimestamp} y se almacenan con TTL de windowSecs * 2. Cloudflare KV las elimina automáticamente al vencer el TTL, pero en escenarios de alto tráfico el namespace puede acumular miles de claves simultáneas.
Impacto
Nulo en seguridad. El costo operativo de KV en Cloudflare es por operaciones, no por número de claves — no hay riesgo de costos inesperados a la escala actual del producto.
Recomendación
Sin acción requerida. Cloudflare gestiona la limpieza automáticamente vía TTL.
OBS-03 worker.js como punto único de routing — sin tests automatizados Bajo riesgo
Severidad
Bajo
Descripción
worker.js actúa como router central para /validate-license, /trial, /sync, /backup. No hay tests unitarios ni de integración — los cambios solo se validan en producción.
Impacto
Un error en el routing podría silenciosamente redirigir tráfico de un endpoint a otro. A la escala actual del producto, el riesgo es bajo — el código es simple y el router es minimal.
Recomendación
Agregar al menos un test de smoke vía wrangler dev + curl en el CI como step pre-deploy. Baja prioridad.

⚠️ Riesgos residuales y aceptaciones (sin cambios desde v5)
RR-01 unsafe-inline en script-src / style-src — CSP parcialmente permisivo Aceptado
Severidad
Medio
Motivo
La app es una SPA monolítica con todo el JS/CSS inline. Migrar a nonces requeriría un servidor dinámico y refactorización mayor.
Mitigación activa
COOP + CORP + X-Frame-Options DENY + no eval — reduce el riesgo de explotación si existiera un XSS desconocido.
RR-02 Datos almacenados en IndexedDB sin cifrado Aceptado
Severidad
Medio
Motivo
Cifrado client-side requiere gestión de claves de usuario — complejidad alta con potencial de pérdida de datos. El modelo de amenaza (resellers individuales) no justifica el overhead.
Mitigación activa
PIN de 6 dígitos con sal aleatoria por dispositivo, HTTPS obligatorio (HSTS), COOP/CORP limita acceso entre origins.
RR-03 Subrecursos externos (OneSignal, Google Fonts, Cloudflare) sin SRI Bajo riesgo
Severidad
Bajo
Contexto
Los CDN en uso tienen SLA de integridad y son ampliamente monitoreados. SRI bloquearía actualizaciones automáticas de estos proveedores.
Mitigación activa
CSP allowlist explícita limita el origen de los scripts.

Medio
