✓ Mejoras corregidas en v4
SW-01
Ruta /trial excluida del caché del Service Worker
v4
La ruta /trial fue añadida a la lista de rutas API excluidas del caché en worker.js. Sin esta exclusión, respuestas de validación de licencia podían quedar almacenadas en caché, permitiendo que una verificación exitosa previa persistiese offline de forma indefinida.
// worker.js — API_ROUTES (v4) const API_ROUTES = ['/api/', '/backup', '/trial'];
HDR-01
Cabeceras de seguridad HTTP ampliadas en _headers
v4
Se añadieron seis cabeceras y directivas CSP que refuerzan el aislamiento de origen y la política de transporte. Bloquean ataques de ventanas emergentes (Spectre/XS-Leaks), lectura de recursos cross-origin y downgrade de protocolo.
Cross-Origin-Opener-Policy: same-origin Cross-Origin-Resource-Policy: same-origin Strict-Transport-Security: max-age=63072000; includeSubDomains; preload X-Permitted-Cross-Domain-Policies: none # Nuevas directivas CSP: base-uri 'self' form-action 'self'
LIC-01
Validación de formato en activarLicencia() antes del envío
v4
La función activarLicencia() ahora valida el formato del código con una expresión regular antes de realizar cualquier llamada al servidor. Previene el envío de entradas malformadas o con caracteres especiales que podrían emplearse en inyecciones o fuzzing.
// activarLicencia() — validación previa al fetch const CODE_RE = /^[A-Z0-9\-]{5,64}$/; if (!CODE_RE.test(codigo.trim())) { return mostrarError('Formato de código inválido'); }
VAL-01
Límites de longitud en campos de texto de ventas
v4
La función _validateVenta() aplica límites estrictos de longitud en todos los campos de texto libre, reduciendo la superficie de ataque de payloads grandes que afectan al almacenamiento local, exportaciones y renderizado.
// _validateVenta() — límites de longitud (v4) perfume: máx. 120 chars cliente: máx. 100 chars vendedor: máx. 80 chars nota: máx. 500 chars proveedor: máx. 100 chars
VAL-02
Límite de 120 chars en nombre de perfume al editar
v4
La función guardarEdicionPerfume() impone un tope de 120 caracteres en el nombre. Era inconsistente con la validación de ventas y abría una vía para insertar cadenas largas que podían afectar el renderizado y la búsqueda interna.
// guardarEdicionPerfume() — v4 if (nombre.length > 120) { return mostrarError('Nombre demasiado largo (máx. 120)'); }
✓ Mejoras históricas — v2 y v3 (base consolidada)
▼
ℹ Hallazgos corregidos en versiones anteriores que constituyen la base de seguridad actual. Se incluyen por trazabilidad y auditoría histórica.
V-01/V-06
XSS en campos vendedor y descuento
v3
Campos de texto renderizados sin escapar permitían inyección de HTML arbitrario en la tabla de ventas. Corregido aplicando escapeHTML() en todos los puntos de interpolación de la vista.
// v3 — aplicado en todos los campos de la vista cell.textContent = escapeHTML(v.vendedor); cell.textContent = escapeHTML(String(v.descuento));
V-05
Objeto LICENSE congelado con Object.freeze()
v3
El objeto global LICENSE era mutable desde la consola del navegador. En v3 se protegió con Object.freeze() para evitar modificación en tiempo de ejecución mediante DevTools.
// v3 — protección del objeto de licencia Object.freeze(LICENSE);
V-08
Rutas /backup en API_ROUTES del SW
v3
La ruta /backup no estaba en la lista de exclusión del caché, permitiendo descargas de backup desde caché stale. Corregido en v3; la exclusión de /trial completada en v4 (ver SW-01).
V-09
Eliminado unsafe-eval del CSP
v3
La directiva script-src incluía unsafe-eval, habilitando la ejecución de código dinámico vía eval() y new Function(). Eliminado en v3, cerrando una clase completa de ataques XSS de segundo orden.
V-11
Sanitización de data fields en send-email.js
v3
Los campos enviados al worker de email no eran sanitizados antes de la construcción de la petición, abriendo potencial header injection. Corregido en v3 con sanitización explícita de todos los campos en el punto de entrada del worker.
V-12
Intervalo trial migrado a closure privado
v3
window._trialTickerInterval era accesible desde consola, permitiendo cancelarlo manualmente para detener el countdown del trial. Reemplazado por una variable de closure inaccesible desde el scope global.
// v3 — closure en lugar de window._trialTickerInterval (function initTrialTicker() { const interval = setInterval(tick, 1000); // interval no expuesto en window })();

⚠ Riesgos residuales — inherentes a la arquitectura PWA
⚠ Los siguientes riesgos son consecuencia directa del modelo PWA offline-first y no representan bugs corregibles sin rediseñar la arquitectura fundamental de la aplicación.
V-02
IndexedDB editable con DevTools
Residual
Los datos de negocio almacenados en IndexedDB (ventas, inventario, configuración) pueden leerse y modificarse directamente desde el panel "Application" de DevTools del navegador por cualquier usuario con acceso al dispositivo.
ℹ Inherente a todas las PWAs. IndexedDB no puede cifrarse con clave derivada del usuario sin degradar la experiencia offline. El dato no sale del dispositivo del operador; el riesgo es físico, no remoto.
V-03
Trial offline usa timestamp local como fallback
Residual
Cuando el dispositivo está offline, la verificación del período de trial cae back al reloj local del SO. Un usuario técnico puede manipular la fecha del sistema para extender artificialmente el período de prueba.
ℹ Inevitable en PWAs con soporte offline real. La alternativa (bloqueo total sin conexión) elimina la propuesta de valor. El servidor re-verifica y puede revocar en el próximo check online.
V-04
PIN reseteable borrando localStorage
Residual
El PIN de acceso local puede eliminarse borrando las entradas correspondientes de localStorage desde DevTools. La aplicación solicitará un nuevo PIN en el siguiente arranque.
ℹ El PIN es un mecanismo de conveniencia (evitar accesos accidentales), no un control de seguridad fuerte. Quien tiene acceso físico al dispositivo tiene acceso a los datos de todas formas. Documentado como "bloqueo de pantalla de conveniencia".
V-07
Firma ECDSA almacenada en localStorage
Arquitectural
La firma ECDSA que acredita la licencia activa se persiste en localStorage para permitir la verificación en modo offline. Es visible y copiable desde DevTools. No impide el funcionamiento offline de la app legítima.
ℹ Requerido por diseño: sin la firma local no existe validación offline. La firma solo prueba que el servidor emitió la licencia en algún momento; el servidor puede revocarla en el siguiente check online. No es explotable por terceros sin acceso físico al dispositivo.
V-10
Número de WhatsApp en código fuente
Info
El número de contacto de soporte vía WhatsApp está hardcodeado en el JavaScript del cliente y es visible en el código fuente (incluso minificado).
ℹ No es una vulnerabilidad de seguridad. El número es público y su exposición en el source es equivalente a publicarlo en la página de contacto del producto. No requiere acción correctiva.
