🔴 Vulnerabilidades críticas
01
Bypass total de licencia via window._activationVerified
CRÍTICO Frontend OWASP A01 - Broken Access Control

Descripción: La función isActivated() (línea 11879) retorna simplemente window._activationVerified === true. Esta variable global controla el acceso a todas las funciones premium: registrar ventas ilimitadas, exportar CSV, backup cloud, estadísticas completas. Al ser una variable window., cualquier usuario con acceso a DevTools puede escribir una línea y obtener acceso completo sin licencia, sin trial, sin límites.

Cómo explotarlo (< 5 segundos):

// En la consola del navegador (F12):
window._activationVerified = true

// RESULTADO: acceso ilimitado instantáneo.
// La app cree que el usuario tiene licencia activada.
// Funciona aunque el trial esté vencido.
// Persiste hasta el próximo reload.

Variante persistente: Combinado con un Service Worker custom inyectado via extensión del navegador, o un bookmarklet, el atacante puede re-ejecutar esto en cada carga de página automáticamente.

Impacto real: 100% de las restricciones de licencia son nulas. Un video de TikTok de 30 segundos explicando cómo hacerlo sería suficiente para que cientos de usuarios lo repliquen. Pérdida directa de ingresos por cada usuario que lo descubra.

Solución: No usar variables globales para controles de acceso. Encapsular el estado en un closure privado. La lógica de licencia debe estar en una IIFE o módulo ES que no exponga ninguna variable a window. Además, re-verificar la firma ECDSA en los puntos de acceso críticos (no solo en el boot), con un cooldown para evitar abuso de crypto.

02
Reset infinito del trial via limpieza de almacenamiento
CRÍTICO Frontend OWASP A05 - Security Misconfiguration

Descripción: El trial de 7 días se ancla a localStorage['pt_trial_start'] con fallback a IndexedDB. La protección anti-bypass consiste en anclar al timestamp de la venta más antigua (línea 12001). Sin embargo, ambos storages son accesibles y borrables por el usuario. Si el atacante borra todo, no hay ningún registro server-side y el trial se reinicia.

Cómo explotarlo:

// Método A — Consola del navegador:
await indexedDB.deleteDatabase('parfumtrack_db')
localStorage.clear()
location.reload()
// RESULTADO: trial reiniciado. 7 días más de acceso completo gratis.

// Método B — DevTools → Application → Storage → Clear site data
// RESULTADO: mismo efecto, sin código.

// Método C — Llamar la función de testing que quedó en producción:
resetTrialYDatos()  // Esta función existe como global (línea 12395)

Función de testing expuesta: resetTrialYDatos() existe en el código de producción como función global accesible desde la consola. Borra el trial completo y data demo. Es una puerta trasera accidental.

Impacto real: Trial gratuito infinito para cualquier usuario que conozca este truco. No requiere ningún conocimiento técnico avanzado — limpiar "datos del sitio" en Chrome es un menú de 2 clics.

Solución: 1) Eliminar resetTrialYDatos() de producción o encapsularla en modo debug. 2) Registrar el inicio del trial server-side (en KV) usando un fingerprint de dispositivo o dirección IP+userAgent al primer uso. 3) En cada carga, si el trial_start local no coincide con el server-side, imponer el valor server-side.

03
Licencia nunca revocada — activación válida para siempre
CRÍTICO Backend / Auth OWASP A07 - Identification & Auth Failures

Descripción: El servidor valida la licencia una sola vez y devuelve una firma ECDSA. De ahí en adelante, el cliente verifica esa firma localmente contra la clave pública embebida (línea 11882). El servidor nunca vuelve a ser consultado. Esto significa que:

  • Una licencia no puede ser revocada: si un cliente paga y luego pide chargeback, sigue usando la app
  • El mismo par (code, sig) puede compartirse entre N dispositivos — un usuario puede copiar su localStorage y dárselo a 10 amigos
  • No hay forma de auditar cuántos dispositivos activos hay por licencia

Cómo explotarlo (compartir licencia):

// Dispositivo A (licencia legítima):
JSON.stringify({
  pt_license_raw_code:  localStorage.getItem('pt_license_raw_code'),
  pt_activated_code:    localStorage.getItem('pt_activated_code'),
  pt_activated_sig:     localStorage.getItem('pt_activated_sig'),
  pt_activation_mode:   localStorage.getItem('pt_activation_mode'),
})
// Copiar este JSON y enviárselo a cualquier persona.

// Dispositivo B (sin licencia):
Object.entries(JSON.parse(PEGADO_ARRIBA)).forEach(([k,v]) => localStorage.setItem(k, v))
location.reload()
// RESULTADO: dispositivo B activa la licencia completamente.

Impacto real: Una licencia vendida puede replicarse a infinitos usuarios. Un foro de "cracks" podría publicar las keys de localStorage y anular completamente el modelo de monetización.

Solución: Implementar un heartbeat periódico al backend (cada 7 días) donde el cliente envíe code+token para re-validar. Si la licencia fue revocada en KV, el server responde con valid: false. Esto no evita el uso offline pero limita el abuso.

04
Manipulación directa de datos de negocio via IndexedDB
CRÍTICO Frontend / Storage OWASP A04 - Insecure Design

Descripción: Todos los datos de negocio (ventas, perfumes, stock, gastos, caja) viven exclusivamente en IndexedDB local. No hay ningún servidor que valide o proteja la integridad de esos datos. Un atacante con acceso a DevTools puede modificar cualquier valor.

Cómo explotarlo — manipular una venta para inflar ganancias:

// En DevTools → Application → IndexedDB → parfumtrack_db
// Buscar "vip_ventas_v2_default", abrir, editar objeto

// O via consola:
const req = indexedDB.open('parfumtrack_db', 1);
req.onsuccess = e => {
  const db = e.target.result;
  const tx = db.transaction(['kv'], 'readwrite');
  const store = tx.objectStore('kv');
  const r = store.get('vip_ventas_v2_default');
  r.onsuccess = ev => {
    const ventas = ev.target.result;
    ventas[0].pv = 999999;   // precio de venta
    ventas[0].ganancia = 999999; // ganancia
    store.put(ventas, 'vip_ventas_v2_default');
  };
};
// RESULTADO: estadísticas alteradas, ganancias infladas.

Escenarios de impacto: Un empleado que usa la app puede alterar sus ventas para parecer más productivo. Un revendedor puede manipular su caja para ocultar pérdidas. Datos fiscales falseados.

Nota importante: Esto es un riesgo inherente a las apps 100% client-side. No es completamente solucionable sin mover los datos a un servidor con autenticación. Sin embargo, el backup en la nube (R2) puede servir como registro de auditoría si se implementa correctamente.

Solución parcial: Implementar checksums locales de la data (firmados con la clave de licencia) para detectar manipulación. Más completo: servidor de sincronización con validaciones server-side.

🟠 Vulnerabilidades altas
05
Manipulación del timestamp de ventas para bypass del límite post-trial
ALTO Frontend / Lógica

Descripción: Cuando el trial vence, la app permite seguir cargando hasta 5 ventas más (trialLimitedVentas = 5). El conteo usa v.createdAt comparado con la fecha de vencimiento del trial (línea 11983). Si un atacante modifica los createdAt de esas ventas para que sean anteriores al vencimiento, el contador llega a 0 y puede registrar ventas infinitamente más.

// Modificar createdAt de todas las ventas post-trial para parecer anteriores:
const req = indexedDB.open('parfumtrack_db', 1);
req.onsuccess = e => {
  const tx = e.target.result.transaction(['kv'], 'readwrite');
  const store = tx.objectStore('kv');
  const r = store.get('vip_ventas_v2_default');
  r.onsuccess = ev => {
    const ventas = ev.target.result.map(v => ({
      ...v,
      createdAt: Date.now() - 999999999  // poner en el pasado
    }));
    store.put(ventas, 'vip_ventas_v2_default');
  };
};

Solución: Los timestamps de ventas deben ser inmutables una vez creados, o validados contra el timestamp del sistema al momento de guardar. Considerar firmar cada venta con un hash que incluya su timestamp.

06
PIN de seguridad bypasseable — almacenado en localStorage
ALTO Auth OWASP A07

Descripción: El PIN protege el acceso a la app. El hash SHA-256 del PIN se guarda en localStorage['pt_pin_hash']. El mecanismo de lockout (pt_pin_fails, pt_pin_lockout) también está en localStorage. Cualquier persona con acceso a DevTools puede:

// Bypass completo del PIN:
localStorage.removeItem('pt_pin_hash')
location.reload()
// RESULTADO: la app asume que no hay PIN configurado y entra directamente.

// Alternativa — resetear el contador de intentos fallidos:
localStorage.removeItem('pt_pin_fails')
localStorage.removeItem('pt_pin_lockout')
// RESULTADO: lockout eliminado, se pueden hacer infinitos intentos.

Salt hardcodeado: El salt es "pt_salt_2026_" para todos los usuarios. Un atacante puede precomputar un rainbow table para PINs de 4-6 dígitos (solo 10^6 posibilidades) con este salt conocido y crackear cualquier PIN robado.

Solución: El PIN solo puede proteger contra alguien que no tiene acceso a los DevTools del dispositivo. Para ese caso, es suficiente. Documentar esto como limitación conocida. Para una protección real, el PIN debería derivar una clave de cifrado AES que proteja los datos en reposo (los datos en IndexedDB deberían estar cifrados con esta clave).

07
Inyección de datos via backup cloud restaurado
ALTO Backend / Data OWASP A03 - Injection

Descripción: La validación del backup (_validarSchemaBackup()) solo verifica que los arrays sean arrays y que algunos campos numéricos no sean NaN. No hay límite de longitud en strings, no hay restricción de propiedades extra, no hay sanitización profunda. Un atacante que tenga acceso al backup (o lo intercepete en tránsito) puede inyectar objetos con propiedades maliciosas que se guardan en IndexedDB.

Vectores: Si el servidor de backup es comprometido (aunque actualmente R2 no está activado), o si se explota el endpoint POST /backup con una licencia válida copiada, se pueden insertar datos maliciosos que persisten en el dispositivo.

Solución: Validar exhaustivamente cada objeto venta/perfume/gasto antes de importar: maxLength en todos los strings (máx 500 chars), whitelist de propiedades permitidas (eliminar extras), rangos numéricos estrictos.

🟡 Vulnerabilidades medias
08
Sin Content Security Policy (CSP) — XSS amplificado
MEDIO OWASP A05 - Security Misconfiguration

El HTML no tiene headers Content-Security-Policy ni meta-tag CSP. Si se encuentra cualquier XSS (actualmente no hay evidencia de uno), no hay ninguna barrera adicional que limite lo que puede ejecutar el script inyectado. Un XSS podría exfiltrar localStorage completo, incluida la activación de licencia.

Solución: Agregar header CSP via Cloudflare Pages (_headers file): Content-Security-Policy: default-src 'self'; script-src 'self' 'sha256-...'; connect-src 'self' https://plausible.io ...

09
Sin validación de longitud máxima en campos de venta
MEDIO Data Integrity

addVenta() valida rangos numéricos pero no longitudes de strings. Un atacante puede guardar un nombre de perfume de 1MB que: (a) llena el storage del dispositivo, (b) causa lag en el render de la lista de ventas, (c) ocupa ancho de banda en el backup cloud.

// Insertar venta con datos masivos:
document.getElementById('inp-perfume').value = 'A'.repeat(500000)
addVenta()  // pasa validación, se guarda

Solución: Agregar maxlength HTML en todos los inputs + validación JS: perfume max 200 chars, cliente max 150, nota max 1000.

10
Salt de PIN hardcodeado y predecible
MEDIO Cryptographic Failure

El salt del hash SHA-256 del PIN es "pt_salt_2026_" — idéntico para todos los usuarios. Cualquier atacante que robe el hash (pt_pin_hash) puede precomputar todos los PINs de 4-6 dígitos con este salt conocido (10^6 combinaciones, < 1 segundo en GPU) y crackear el PIN sin necesidad de intentos en la app.

Solución: Generar un salt aleatorio de 16 bytes al crear el PIN y guardarlo junto al hash: localStorage['pt_pin_salt'] = crypto.randomUUID().

11
Service Worker cachea el HTML completo — bypass de hotfixes de seguridad
MEDIO PWA Security

El Service Worker implementa Network First para HTML, pero si la red no está disponible, sirve la versión cacheada. Si se descubre una vulnerabilidad crítica y se publica un fix urgente, los usuarios offline (o con conectividad mala) seguirán usando la versión vulnerable por un tiempo indeterminado.

Solución: Implementar un kill switch de versión mínima: en cada carga online, consultar un endpoint /min-version y si la versión local es menor, forzar una recarga hard ignorando caché.

Fix prioritario #1 — Encapsular estado de licencia
Reemplazar el sistema de window._activationVerified con un módulo de licencia encapsulado que no expone ninguna variable a window:
// ANTES (vulnerable):
window._activationVerified = false;
function isActivated() { return window._activationVerified === true; }

// DESPUÉS (seguro):
const LicenseManager = (() => {
  let _verified = false;                  // No accesible desde window
  let _verifiedAt = 0;                    // Timestamp de verificación
  const MAX_AGE_MS = 5 * 60 * 1000;      // Re-verificar cada 5 min

  return {
    setVerified(val) {
      _verified = !!val;
      _verifiedAt = val ? Date.now() : 0;
    },
    isActivated() {
      if (!_verified) return false;
      // Expirar el flag si la pestaña lleva mucho tiempo abierta
      // (fuerza re-verificación ECDSA periódica)
      if (Date.now() - _verifiedAt > MAX_AGE_MS) {
        // Lanzar re-verificación async
        verifyStoredLicense().then(ok => LicenseManager.setVerified(ok));
      }
      return _verified;
    }
  };
})();

// Usar LicenseManager.isActivated() en lugar de isActivated()
// Usar LicenseManager.setVerified(true/false) en lugar de asignación directa
Con este cambio, window._activationVerified ya no existe. El estado de licencia es inaccesible desde la consola. El atacante no puede bypassearlo sin modificar el código fuente (lo que requiere una extensión de navegador más sofisticada).

const trialKey = `trial:ip:${ip}`;
