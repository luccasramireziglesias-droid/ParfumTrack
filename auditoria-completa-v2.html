Resumen Ejecutivo

Parfum Track es una PWA para gestión de ventas de perfumes, orientada a revendedoras LATAM. Stack: Cloudflare Workers + KV + R2 + Brevo + OneSignal + MercadoPago Checkout Pro. App monolítica de ~19.000 líneas (index.html), todo el backend en funciones serverless.

CSP 'unsafe-inline' en script-src — anula protección XSS
_headers
Archivo_headers línea 10
ImpactoSi existe un XSS (por un innerHTML sin escapeHTML), el atacante puede ejecutar JS arbitrario, leer localStorage (tokens HMAC, ECDSA sig, sync token) y exfiltrarlos.
CausaEl app tiene miles de líneas con innerHTML. Para evitar romper todo al agregar CSP estricto, se dejó 'unsafe-inline'. Esto vacía la protección CSP.
Solución exactaMigrar a nonces o hashes de script. En Cloudflare Workers, generar un nonce por request y pasarlo al HTML. Alternativamente, mover todos los scripts inline a un archivo app.js externo (permite eliminar 'unsafe-inline').
DificultadAlta — requiere refactor de la app monolítica. Largo plazo.
Impacto esperadoEleva score de seguridad de 78 → 88+ una vez resuelto.

ctx.waitUntil sin confirmación de procesamiento — riesgo de pagos perdidos
mp-webhook.js
Archivofunctions/mp-webhook.js L83
ImpactoEl webhook responde 200 inmediatamente y procesa en background. Si el Worker runtime termina antes de que ctx.waitUntil complete (timeout de CF, deploy, etc.), el pago se marca como "processing" y queda atascado 5 minutos hasta que MP reintente. MP reintenta máx. 3 veces — si los 3 intentos caen en ventanas de timeout, el pago no se procesa.
CausaComportamiento intrínseco de Cloudflare Workers con ctx.waitUntil. No es un bug sino una limitación arquitectural.
Solución exactaLa idempotencia ya está bien implementada (cleaning en caso de error, TTL de 5 min en "processing"). Para mayor robustez: agregar una Cloudflare Durable Object o Queue como buffer. Corto plazo: reducir el TTL de "processing" a 120 segundos.
DificultadMedia.
Medio
Tokens sensibles en localStorage — exfiltrable por XSS
index.html
Archivoindex.html L11824-11828
Impactopt_activated_code (HMAC token para backup), pt_activated_sig (ECDSA sig), pt_sync_token son accesibles vía localStorage desde cualquier JS en la página. Si existe un XSS, el atacante puede robar estos tokens y hacer backups o sincronizaciones no autorizadas.
Mitigación existenteECDSA client-side verification, escapeHTML() en todos los campos de usuario, CSP (aunque débil por unsafe-inline). El HMAC token solo permite operaciones de backup — no otorga acceso a la cuenta MP ni datos del servidor.
CausaLimitación de PWAs — no hay httpOnly cookies ni Secure storage disponible en contexto de webapp pura.
Solución exactaShort term: limpiar tokens al cerrar sesión (sessionStorage en vez de localStorage para sync token). Long term: resolver unsafe-inline primero.
DificultadMedia.

Race condition en rate limiter — KV no es atómico
Todos los endpoints
ImpactoBajo carga alta (>10 requests simultáneos por IP), dos requests pueden leer el mismo contador antes de que alguno escriba, bypaseando levemente el rate limit. En práctica, con los límites actuales (5-20 req/hr), esto es aceptable.
CausaCloudflare KV no soporta operaciones atómicas (compare-and-swap). Es una limitación del storage.
SoluciónUsar Cloudflare Durable Objects para rate limiting atómico si se requiere mayor precisión. No urgente para el volumen actual.

Fase 2 — Auditoría Técnica Detallada

✅ Fortalezas detectadas

  • HMAC-SHA256 timing-safe para tokens
  • ECDSA P-256 client-side (sin red en cada uso)
  • Idempotencia completa en webhook (processing → done/retry)
  • Rate limiting en TODOS los endpoints
  • Validación de monto en webhook (protege contra pago parcial)
  • 2-minute polling timeout con fallback visual
  • OTP de 6 dígitos con 5 intentos máx + delay anti-brute-force
  • HSTS preload + X-Frame-Options DENY
  • EscapeHTML() usado consistentemente en innerHTML
  • Secrets fuera del código (CF Dashboard)
  • R2 backup con auth token HMAC
  • Service Worker con Network-First para HTML

⚠ Deuda técnica detectada

  • App monolítica de 19k líneas — difícil de mantener
  • Funciones duplicadas (corsHeaders, checkRateLimit, timingSafeEqual en 7 archivos)
  • send-notification.js no usa el subscriptionId del usuario logueado — lo recibe del cliente (sin auth)
  • Legacy trial path sin OTP expone trial a usuarios sin email
  • No hay versión mínima del manifest de Chrome para PWA install
  • wa.me URLs construidos con concatenación directa (sin encodeURIComponent consistente)
  • CACHE_NAME hardcoded como "parfumtrack-v4" — requiere cambio manual en deploy
