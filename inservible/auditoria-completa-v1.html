Los 3 hallazgos críticos de seguridad fueron detectados y corregidos en esta misma sesión de auditoría. No quedan vulnerabilidades críticas abiertas.

✅ CORREGIDO
XSS almacenado — fecha de última venta en tarjeta de cliente
ln 2219
ultVenta?.fecha se insertaba en innerHTML sin pasar por escapeHTML(). Un backup importado con fecha: "<img src=x onerror=alert(1)>" ejecutaría JS arbitrario al renderizar la lista de clientes.
Fix aplicado: ${escapeHTML(ultVenta?.fecha||'—')}
✅ CORREGIDO
XSS almacenado — fecha en detalle de venta de cliente
ln 2287
v.fecha sin escapar en el modal de detalle de cliente, mismo vector que el anterior.
Fix aplicado: ${escapeHTML(v.fecha||'')}
✅ CORREGIDO
CORS wildcard permite cualquier subdominio de Netlify / Pages / Workers
4 archivos
El patrón .*\.netlify\.app, .*\.pages\.dev, .*\.workers\.dev en los 4 endpoints permitía que cualquier app alojada en esas plataformas llamara a la API. Aunque el auth por token mitiga el impacto, no es el CORS mínimo necesario.
Fix aplicado: whitelist restringida a parfumtrack.pages.dev y parfumtrack.workers.dev en validate-license.js, backup.js, send-email.js y worker.js
✅ CORREGIDO
Credenciales OneSignal reales en comentarios de código
send-notification.js ln 7-8
El ONESIGNAL_REST_KEY (clave secreta de la API REST de OneSignal) estaba expuesto en un comentario del archivo fuente, visible en el repositorio.
Fix aplicado: reemplazado por placeholders descriptivos
🟡 MEDIO
DELAY_ON_INVALID de 600ms en validate-license puede ser insuficiente
validate-license.js ln 16
El delay de 600ms frena intentos secuenciales de brute-force, pero en ataques distribuidos (múltiples IPs simultáneas) podría ser insuficiente. El formato de código PT-XXXXXX-YYYYYY tiene ~2 billones de combinaciones posibles, así que el riesgo práctico es bajo.
Impacto: BAJO-MEDIO. Mitigado por formato largo del código y KV rate limit por código.
ℹ INFO
timingSafeEqual() correctamente implementado en backup.js
backup.js ln 141-148
La comparación HMAC usa tiempo constante, resistente a timing attacks. Bien implementado.

Autenticación y Autorización
0 críticos · 1 medio · 3 info
8.8

ℹ INFO
Sistema dual-auth ECDSA + HMAC correctamente implementado
ECDSA P-256 para verificación de licencia client-side. HMAC-SHA256 para autenticación de backup server-side. Dos mecanismos independientes sin hardcoding de secretos en código fuente.
ℹ INFO
PIN con lockout de 5 intentos y bloqueo de 5 minutos
ln 4774-4810
SHA-256 con salt estático (pt_salt_2026_ + PIN). MAX_FAILS = 5, LOCKOUT_MS = 300.000ms. El contador persiste entre recargas vía localStorage. Nunca se guarda el PIN en claro.
🟡 MEDIO
Trial anclado a timestamps del cliente — manipulable
ln 3473-3494
La antigüedad del trial se determina por el timestamp del ID más antiguo de las ventas (v.id = Date.now()). Un usuario técnico podría manipular el clock del browser o importar un backup con IDs viejos para extender el trial.
Impacto: MEDIO en teoría, BAJO en práctica. El trial es de buena fe — no hay datos valiosos que proteger con el trial.
ℹ INFO
Token de backup no puede ser forjado sin LICENSE_SERVER_SECRET
backup.js ln 150-165
El token es HMAC-SHA256(code, secret). Sin la clave en Cloudflare env vars, un atacante no puede generar tokens válidos. La verificación usa comparación en tiempo constante.

Funcionalidad
0 críticos · 2 medios · 2 info
8.7

ℹ INFO
Cálculos financieros matemáticamente correctos
Ganancia usa Math.round(pv - pc) — sin acumulación de flotantes. Cuotas distribuyen saldo restante proporcionalmente. calcDebe() con Math.max(0, ...) previene valores negativos.
🟡 MEDIO
calcDebe() devuelve 0 ante sobrepagos — sin registro de crédito
ln 1837
Si en un backup importado una cuota tiene cuotasPagos.monto > precioVenta, la función devuelve 0 (correcto para deuda) pero no registra el crédito a favor del cliente. En uso normal no ocurre porque la UI no permite ingresar montos superiores al debe.
Impacto: BAJO. Solo reproducible con backup manipulado.
🟡 MEDIO
Importación Excel sin validación de valores negativos
~ln 3072
La función confirmImport() no valida que precioVenta y precioCompra sean no-negativos. Un Excel con precios negativos generaría ganancias inconsistentes. La validación existe en el formulario de nueva venta, pero no en la importación.
Impacto: MEDIO. Puede generar estadísticas incorrectas si el Excel tiene errores.
ℹ INFO
Backup/restore con rollback automático y validación de schema
ln 2010-2052
Antes de restaurar se descarga copia local. El schema valida tipos de campos (arrays, números, strings). Bien implementado.

🟡 MEDIO
Error de IndexedDB muestra pantalla de carga infinita
~ln 5036
Si IndexedDB falla al inicializar, el .catch() existe pero solo hace console.error. El usuario ve la app cargando indefinidamente sin mensaje de error.
Impacto: MEDIO. Poco frecuente, pero bloquea completamente la app cuando ocurre.
🟡 MEDIO
OneSignal importScripts en SW sin manejo de error
sw.js ln 2
importScripts('https://cdn.onesignal.com/...') al inicio del service worker. Si el CDN falla o está bloqueado por el firewall del usuario, todo el SW falla y la app pierde funcionalidad offline.
Impacto: BAJO-MEDIO. Las notificaciones push son secundarias; el SW no debería depender de un CDN externo para cargar.
ℹ INFO
Todas las llamadas fetch() tienen AbortSignal.timeout() o try/catch
cloudBackupSave (15s), cloudBackupRestore (15s), activarLicencia (6s), todos tienen timeout y manejo de error con toast. Los guards _backupInFlight previenen llamadas concurrentes.

Performance

ℹ INFO
Debounce aplicado a todos los inputs de búsqueda/generación
Ventas (280ms), stock (280ms), catálogo (200ms), canvas catálogo (350ms), foto URL (400ms), gastos (260ms). Todos los renders costosos están debounceados.
🟡 MEDIO
renderClientes() reconstruye mapa de todas las ventas en cada render
~ln 2145-2175
Itera todas las ventas para construir el mapa de clientes cada vez que se renderiza la pestaña. Para 1.000 ventas no hay impacto; con 10.000+ puede producir lag visible.
Impacto: BAJO para uso actual. Agregar memoización cuando supere 5.000 ventas.
🟡 MEDIO
calcDebe() y diasDesdeUltimoPago() llamadas 3–4× por ítem en renderCuotasPendientes()
~ln 2617
Para ordenar y agrupar las cuotas se llama diasDesdeUltimoPago() en el sort, en los 3 filtros, y luego de nuevo en el render de cada card. Pre-calcular una sola vez ahorraría O(n log n) llamadas extra.
Impacto: BAJO. Con menos de 200 cuotas activas, imperceptible.
ℹ INFO
Lazy-load de jsPDF, XLSX y Chart.js correctamente implementado
Las tres librerías pesadas se cargan dinámicamente solo cuando el usuario las usa por primera vez. El bundle inicial es solo index.html + sw.js + manifest.

ℹ INFO
Touch targets ≥ 44px en todos los elementos interactivos

CSS base: min-height:44px en .btn-primary, .btn-outline, input, select. El botón WA en cuotas también corregido con min-height:44px.
🟡 MEDIO
Sin notificación de "actualización disponible" cuando hay nueva versión del SW
Cuando se deploya una nueva versión, el service worker actualizado no notifica al usuario hasta que cierra y reabre la app. El usuario puede estar usando una versión vieja sin saberlo.
Impacto: BAJO-MEDIO. Afecta la experiencia de recibir features nuevas.
🟡 MEDIO
Botón "Guardar venta" no se deshabilita si faltan campos requeridos
La validación ocurre solo al hacer click, no en tiempo real. El usuario puede intentar guardar, recibir un error, corregir el campo y volver a intentar. No es un bug bloqueante, pero aumenta la fricción en mobile.
Impacto: BAJO. Funciona correctamente — solo es experiencia subóptima.
ℹ INFO
Toast queue implementado — los mensajes se secuencian sin pisarse
ln 1757-1774
Cola FIFO que muestra toasts uno a la vez. Si llega uno nuevo mientras hay otro visible, espera a que el anterior termine (con transición de 300ms).
ℹ INFO
Operaciones destructivas protegidas con confirmación
ln 4394-4407
Reset de app requiere doble confirmación + ingreso manual de texto. Eliminación de ventas/gastos/movimientos tiene sistema de undo con ventana de 6 segundos.

Datos y Persistencia
0 críticos · 2 medios · 2 info
8.0
▼
ℹ INFO
Multi-perfil con aislamiento completo en IndexedDB
ln 4491-4501
Cada perfil usa su propia key en PTDB: profileKey('vip_ventas_v1'). Los datos de un perfil no se mezclan con los de otro. PIN, licencia y trial son globales y se preservan ante resets.
🟡 MEDIO
Sin migración automática si cambia el schema de datos
Si en una versión futura se agrega un campo requerido al schema de ventas o perfumes, los datos existentes no tendrían ese campo. No hay función de migración versión-a-versión.
Impacto: MEDIO para el largo plazo. Bajo riesgo hoy — el schema está estable.
🟡 MEDIO
localStorage puede llenarse con datos grandes
El backup de activación, el draft de nueva venta, los filtros activos, y los settings están en localStorage. Si el usuario tiene miles de ventas y hace backup frecuente, podría acercarse al límite de 5-10MB de algunos browsers.
Impacto: BAJO. La mayoría de los datos van a IndexedDB. localStorage solo guarda metadatos pequeños.
ℹ INFO
save() con debounce de 500ms y reintentos implementado
ln 1664
Escrituras a IndexedDB están debounceadas para evitar escrituras repetidas. La función _saveNow() tiene retry pattern.

PWA / Service Worker

ℹ INFO
Network First para HTML — el usuario siempre recibe la última versión
sw.js ln 39-47
La estrategia de caché para navegación es Network First: intenta la red primero y cae al cache solo cuando está offline. Esto garantiza que los deploys lleguen inmediatamente.
ℹ INFO
Rutas API correctamente excluidas del caché
sw.js ln 36
/validate-license, /backup, /send-email, /send-notification nunca se cachean. Las respuestas de API siempre van a la red.
🟡 MEDIO
importScripts de OneSignal CDN puede bloquear el SW si falla
sw.js ln 2
importScripts() es síncrono — si el CDN de OneSignal está caído o bloqueado (por adblocker, firewall), el SW falla al cargar completamente. La PWA pierde capacidad offline.
Impacto: BAJO-MEDIO. Los datos del usuario están en IndexedDB y no se pierden, pero la experiencia offline falla.
ℹ INFO
Manifest.json completo con todas las propiedades PWA
start_url, display: standalone, iconos de 192px y 512px, shortcuts configurados, theme_color, background_color. Cumple todos los requisitos para instalación como PWA.
