🔴 Bugs confirmados
Toast de stock bajo se dispara en cada decremento
Si el mínimo es 3 y el stock baja de 5→4→3→2→1, el usuario recibe 3 toasts molestos. Debería dispararse solo al cruzar el umbral por primera vez.
index.html · línea ~2555
Trial ticker interval no se limpia al cambiar de perfil
Cada cambio de perfil apila un nuevo setInterval() que corre cada segundo. Con 5 cambios de perfil hay 5 timers corriendo simultáneamente → degradación de rendimiento + lógica errática en el banner de trial.
index.html · renderAjustes / showTab
JSON.parse sin try/catch en restore del backup cloud
Si el objeto en R2 está corrupto o fue escrito parcialmente, JSON.parse(await obj.text()) en backup.js línea 82 tira una excepción no capturada → HTTP 500 sin cuerpo → el cliente ve "Error desconocido" sin poder diagnósticar.
functions/backup.js · línea 82
KV namespace ID es placeholder en producción
"id": "REEMPLAZAR_CON_ID_REAL" en wrangler.jsonc hará que la validación de licencias falle silenciosamente en deploy. El sistema funcionará en trial para siempre o nunca activará licencias.
wrangler.jsonc · línea 25
🟠 Casos límite sin manejo
Excel export accesible para usuarios Starter
La función exportExcel() existe sin gate de tier. La landing la vende como Pro+ pero cualquier Starter puede invocarla desde DevTools o si alguien comparte el link directo.
index.html · ~línea 2514
Venta con precio de compra mayor al de venta
No hay validación que avise si precioCompra > precioVenta. Se puede guardar una venta con ganancia negativa silenciosamente, distorsionando todas las estadísticas de ganancias.
index.html · formulario nueva venta

Si el usuario tiene el backup automático en "diario" y abre la app varias veces al día, cada apertura verifica la fecha y si algo falla con el timestamp, descarga múltiples .json al celular sin confirmación.

Código y Arquitectura
4.5 / 10
🔴 El elefante en la sala: un archivo de 7.000 líneas
Todo — HTML, CSS, JS, lógica de negocio, vistas, modelos, controladores — está en un solo archivo de 7.005 líneas. Esto es técnicamente funcional hoy, pero es el mayor riesgo del proyecto a mediano plazo.

¿Qué rompería primero? La mantenibilidad. Agregar una feature nueva requiere encontrar el lugar correcto en 7.000 líneas. Un bug puede estar en cualquier parte. No se pueden hacer tests unitarios. Dos desarrolladores no pueden trabajar en paralelo sin conflictos de merge masivos.

¿Escalaría a miles de usuarios? El backend sí (Cloudflare Workers escala infinitamente). El frontend no — el archivo de 7K líneas se carga completo en cada usuario, sin code splitting, sin lazy loading de módulos, sin tree shaking.
✅ Lo bueno
• escapeHTML() usado consistentemente (protege de XSS)
• debounce() para búsquedas
• IndexedDB con abstracción PTDB
• Service Worker bien estructurado
• Modales con focus trap y ARIA
• crypto.subtle para PIN (no MD5)
• Constantes de licencia bien separadas
• escapeHTML en innerHTML
🔴 Lo crítico
• 0% cobertura de tests
• Sin bundler / build system (no minificación)
• Sin módulos ES6 (todo en scope global)
• Funciones de 200+ líneas inline (ej: renderVentas)
• Estado global mutable compartido entre funciones (ventas, perfumes, gastos)
• Sin separación de capas (UI + lógica + datos mezclados)
• CSS inline en HTML (mantenimiento imposible a escala)
"Este código funciona excelente para un MVP de un solo desarrollador. Pero si esta app crece, el primer contratado va a tardar 2 semanas solo en entender la estructura. Y el primer refactor va a ser reescribir todo desde cero."
— Perspectiva Arquitecto de Software

📊 Estimados de carga
index.html: ~450-600 KB sin comprimir (7K líneas)
Con gzip/brotli: ~120-180 KB (Cloudflare Pages comprime automáticamente)
app-screenshot.jpg: 472 KB — demasiado grande
jsPDF (lazy): ~250 KB cargado solo cuando se genera PDF ✅

Time to Interactive (3G): ~3-5 segundos estimado
Time to Interactive (4G): ~1-2 segundos estimado
En teléfono lento (Moto G4): ~4-6 seg render + JS parse
⚠️ Problemas de rendimiento
• app-screenshot.jpg = 472 KB — debería ser WebP, max 80 KB
• index.html sin minificar — 450+ KB vs ~120 KB minificado
• CSS no crítico no diferido — todo el CSS carga bloqueando render
• OneSignal SDK externo carga en startup aunque solo Pro lo usa
• renderVentas() re-renderiza todo el DOM en cada keystroke de búsqueda (aunque con debounce 280ms)
• No hay virtualización de listas — con 500+ ventas, el DOM se infla masivamente
🟢 Optimizaciones ya presentes
Service Worker con cache-first para assets estáticos · IndexedDB (no localStorage para datos pesados) · jsPDF lazy-loaded · Lazy loading de imágenes con IntersectionObserver en ventas · Debounce en búsquedas · Compresión de fotos via canvas API

Seguridad
5.0 / 10
🔴 Sin rate limiting en /backup (CRÍTICO)
El endpoint POST /backup no tiene ningún límite de solicitudes por IP o por código. Un atacante puede: (1) probar todos los códigos posibles por fuerza bruta, (2) inundar R2 con backups de 5MB en loop, (3) hacer DoS al servicio sin consecuencias. Costo estimado de ataque: $0. Daño: datos de todos los usuarios accesibles + costos de R2 desbordados.
functions/backup.js — todo el archivo
🔴 Comparación de HMAC no es constant-time
if (token !== expected) es vulnerable a timing attacks. Un atacante con suficientes solicitudes puede determinar el token correcto midiendo tiempos de respuesta. En JavaScript esto es difícil pero no imposible desde un cliente en la misma red. Solución: implementar timingSafeEqual manual.
functions/backup.js · línea 108
🟠 PIN lockout solo client-side
El sistema de 5 intentos antes del bloqueo vive en localStorage. Cualquier usuario puede borrar pt_pin_fails y pt_pin_locked_until desde DevTools en 2 segundos y tener intentos infinitos. En apps de datos financieros esto es un riesgo real.
index.html · recordFail() / isLockedOut()
🟠 Todos los datos financieros en localStorage sin cifrar
Ventas, gastos, precios de compra, nombres de clientes — todo en IndexedDB/localStorage en texto plano. Si el dispositivo es compartido o comprometido, otra app o persona puede leer todos los datos del negocio. En un contexto de revendedoras (muchos comparten teléfono familiar), esto es un riesgo real.
index.html · save() / loadProfile()
🟡 CORS demasiado abierto en backup.js
El allowlist incluye *.pages.dev y *.workers.dev — cualquier deploy de Cloudflare Pages puede hacer requests al endpoint de backup. Debería restringirse solo al dominio de producción real.
functions/backup.js · corsHeaders()
✅ Lo que está bien hecho
PIN hasheado con SHA-256 + salt (no MD5 ni bcrypt plaintext) · escapeHTML() en todos los innerHTML con datos de usuario · Sin eval() en todo el codebase · Secretos del servidor en env vars de Cloudflare (no en código) · HMAC-SHA256 para autenticación de backup (arquitectura correcta) · Validación de formato de token antes de comparar

Negocio y Monetización
7.5 / 10
💚 ¿Por qué la gente pagaría?
• El problema es real y doloroso: las revendedoras de perfumes son un mercado masivo en LATAM que literalmente usa cuadernos
• La app resuelve el problema concreto de "¿cuánto gané este mes?" en 30 segundos vs 2 horas con papel
• El precio ($5-12/mes) es accesible para alguien que vende $50K/mes
• Funciona offline — el mercado al aire libre sin señal es un caso de uso real y diferenciador
• PWA = no requiere app store = cero fricción para instalar
❌ ¿Por qué NO pagaría?
• "Gratis en Excel / Google Sheets" — la percepción de valor vs herramientas gratuitas es el obstáculo #1
• Activación solo por WhatsApp — no hay self-service. Si estoy interesado a las 11pm del domingo, no puedo activar
• Sin app nativa en stores — algunas usuarias no confían en "instalar desde el navegador"
• Sin período de gracia visible — el usuario no sabe qué pasa cuando vence el trial
• Sin prueba social (0 reviews, 0 testimonios visibles)
📈 Potencial real y diferenciación
Mercado objetivo: ~2-5 millones de revendedoras de perfumes en Argentina, Uruguay, Paraguay, Bolivia. Si el 0.5% paga $7/mes → $70K-350K MRR posible.

Diferenciación actual: Vertical muy específico (solo perfumes) + offline-first + precio accesible + WhatsApp integrado. Es una ventaja real vs soluciones genéricas.

Riesgo principal: Excel + Google Sheets + apps gratuitas genéricas de inventario. El costo de cambio para el usuario es bajo porque sus datos están en su celular, no en un server propio.

Oportunidad no explotada: WhatsApp Business API para cobros automatizados. Si la app pudiera enviar el mensaje de cobro automáticamente, el valor percibido se multiplica x3.

¿Lanzarías esta app hoy?
⚠️ Sí, pero con 6 fixes antes del lanzamiento público.
La honestidad brutal: Esta app tiene un producto real para un mercado real con un dolor real. Eso es el 80% de lo que importa en un MVP. El diseño es profesional para ser indie. La funcionalidad core funciona bien.

Lo que la frena: No es el código ni el diseño — es el go-to-market. Sin self-service de pago, sin social proof, con features Business que no existen, y con un agujero de seguridad en el backend, el riesgo de lanzar público es alto.

El path correcto:
1. Arreglar los 6 issues críticos listados arriba (~2-3 horas de trabajo)
2. Conseguir 5-10 usuarios beta que usen la app de verdad durante 2 semanas
3. Tomar sus capturas de pantalla reales y sus palabras reales como testimonios
4. Conectar MercadoPago para activación self-service
5. Lanzar con precio Starter $5/mes y subir cuando haya 20+ usuarios activos

El mayor riesgo no es técnico — es de distribución. Una revendedora de perfumes en Uruguay no va a encontrar esta app en Google. Necesita un canal (TikTok mostrando la app, grupos de WhatsApp de revendedoras, alianzas con mayoristas de perfumes) antes de que el producto importa.
💛 El veredicto honesto del equipo
Con los 6 fixes críticos resueltos, esta app merece lanzarse. El código tiene deuda técnica importante, pero es el tipo de deuda técnica que se puede pagar después cuando hay usuarios que justifiquen la inversión. No al revés.

Score final del equipo: 6.4 / 10 — MVP sólido, listo para beta con fixes críticos.
