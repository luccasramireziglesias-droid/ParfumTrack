🔍 Fase 0 — Comprensión del Proyecto

¿Qué es ParfumTrack?

PWA de gestión comercial para revendedores de perfumes en LATAM (Argentina, Uruguay, Colombia, México). Registro de ventas en 10 segundos, ganancia real automática, control de stock, cuotas, cobros por WhatsApp, catálogo WA, estadísticas. Funciona offline. Sin descarga.

Alcance de esta auditoría

  • Backend: 10 Cloudflare Worker functions + router
  • Infraestructura: wrangler.jsonc, _headers, manifest.json, sw.js
  • Landing: landing.html (~2,200 líneas), checkout pages
  • Legal: privacidad.html, terminos.html
  • Android: MainActivity.java, build.gradle, AndroidManifest.xml, styles.xml
  • Nivel de confianza: Alto — Se leyeron todos los archivos de código fuente

🚨 Top 10 Problemas Críticos

CRÍTICO /send-email sin autenticación — relay de email abierto

Evidencia: functions/send-email.js:253-408 — El endpoint acepta requests sin HMAC token ni license code. Cualquier atacante que conozca un email registrado puede enviar emails a través de la cuenta de Brevo. El rate limit de 5/hr por IP se evade con proxies rotativos.

Fix: Agregar autenticación HMAC idéntica a /send-notification. Requerir code + token en el body y verificar con verifyToken().

CRÍTICO Rate limit con race condition (KV read-then-write no atómico)

Evidencia: Todas las funciones checkRateLimit() — KV get → put no es atómico. Requests concurrentes leen count=0 y todas pasan. Afecta los 10 endpoints.

Fix: Usar Cloudflare Rate Limiting nativo o Durable Objects para contadores atómicos. Aceptar el riesgo con límites más estrictos como alternativa.

ALTO SRI fallback carga scripts SIN verificación de integridad

Evidencia: index.html:16187-16194 — Cuando un script CDN falla SRI, el onerror remueve el script y reintenta la misma URL sin SRI. Un atacante MITM causa fallo SRI (script modificado no matchea hash), triggereando el fallback que carga el script modificado sin verificación.

Fix: Eliminar el fallback sin SRI. Si falla, mostrar error al usuario. Alternativamente, hacer fallback a copia self-hosted.

ALTO Comparación OTP no es timing-safe

Evidencia: functions/trial.js:174 — otpData.otp !== otp usa strict equality que short-circuits, filtrando dígitos correctos via timing. Un atacante puede iterar dígito por dígito reduciendo de 10^6 a ~60 intentos.

Fix: Usar timingSafeEqual() que ya existe en otros archivos del proyecto.

ALTO mp-webhook procesa eventos en background sin retornar error a MercadoPago

Evidencia: functions/mp-webhook.js:86-88 — ctx.waitUntil(processEvent(...)) devuelve 200 inmediatamente. Si processEvent falla, MP no reintenta. Un cliente puede pagar y nunca recibir su licencia.

Fix: Procesar el evento sincrónicamente. Devolver 500 en fallo para que MP reintente. Usar waitUntil solo para side-effects no críticos.

ALTO HMAC token expuesto en URL query parameters

Evidencia: functions/backup.js:89-90, functions/sync.js:102-103 — Tokens en URLs se logean en access logs, browser history y proxies.

Fix: Deprecar autenticación por query params. Aceptar tokens solo via headers X-PT-Code, X-PT-Token.

ALTO HTML injection en templates de email del webhook

Evidencia: functions/mp-webhook.js:362-539 — clientEmail, code, paymentId se interpolan directamente en HTML sin sanitizar. Si un atacante controla el email en MP, puede inyectar HTML/JS en emails.

Fix: Agregar sanitize() (ya existe en send-email.js:206-213) y aplicar a todos los datos del usuario antes de interpolar.

ALTO timingSafeEqual filtra longitud del secreto

Evidencia: functions/validate-license.js:202, backup.js:141, sync.js:153 — if (a.length !== b.length) return false retorna temprano revelando la longitud.

Fix: Padear o hashear ambos strings a longitud fija antes de comparar. Para el owner code, agregar check de formato previo.

ALTO PIN salt no se preserva en reset — lockout permanente

Evidencia: index.html:13914 — _doResetApp() tiene una lista de claves a preservar (pt_pin_hash, pt_pin_locked, pt_pin_attempts) pero NO incluye pt_pin_salt. Después de reset, el salt se pierde y el PIN no puede verificarse nunca más. El usuario queda permanentemente bloqueado.

Fix: Agregar 'pt_pin_salt' al array de preserveKeys en _doResetApp().

ALTO PTDB.clear() destruye datos de TODOS los perfiles

Evidencia: index.html:13912 — PTDB.clear() borra toda la IndexedDB sin filtrar por perfil activo. En multi-perfil, hacer reset con un perfil destruye los datos de todos los perfiles del usuario.

Fix: Implementar clear(profileId) que solo borre los registros del perfil activo, preservando los demás.

ALTO IndexedDB timeout silencioso — datos se pierden sin aviso

Evidencia: index.html:6575 — Si IndexedDB tarda >3s en abrir, db=null silenciosamente. Todas las escrituras subsiguientes son no-ops. El usuario pierde datos sin saberlo.

Fix: Mostrar warning persistente al usuario cuando IndexedDB falla. Implementar fallback a localStorage para datos críticos.

ALTO CSP font-src no incluye 'self' — fuentes locales bloqueadas

Evidencia: _headers:10 — font-src solo permite fonts.gstatic.com. Las fuentes de /fonts/fonts.css (Cormorant Garamond, DM Sans) son bloqueadas por CSP.

Fix: Cambiar a font-src 'self' https://fonts.gstatic.com;

¿Lanzarías el producto?

SÍ, con fixes urgentes en las próximas 24 horas

ParfumTrack es un producto maduro con excelente UX, propuesta de valor clara y monetización funcional. Los 2 hallazgos críticos (email relay abierto y rate limit race) son reparables en horas. Sin embargo, la auditoría profunda de lógica JS reveló 2 bugs altos adicionales: el PIN salt que no se preserva en reset (lockout permanente) y PTDB.clear() que destruye datos de todos los perfiles. El core de la app — ventas, stock, cuotas, estadísticas — es sólido y bien diseñado. La base de código muestra evolución constante (7 auditorías previas, score subiendo de 53 a 95). Los problemas encontrados son típicos de un producto que expandió scope (backend, Android, multi-perfil) más rápido que la capa de seguridad y la validación de datos. Con el plan de 24 horas ejecutado, el producto está listo para escalar.
