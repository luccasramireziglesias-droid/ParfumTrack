🔍 Hallazgos Pendientes
Severidad Alta
ALTO

H-01: Landing OG URLs apuntan a parfumtrack.pages.dev

Problema: Las meta tags og:url, og:image, canonical, twitter:image y el schema.org en landing.html apuntan a "parfumtrack.pages.dev" en vez del dominio real Workers. Plausible analytics también usa el dominio incorrecto. Esto causa previews rotos en redes sociales y analytics duplicados.

Impacto: Pérdida de clicks sociales, SEO duplicado, analytics fragmentados.

Solución: Reemplazar todas las instancias de "parfumtrack.pages.dev" por "parfumtrack.luccasramireziglesias.workers.dev" en landing.html. Verificar que index.html ya usa el dominio correcto.

ALTO

H-02: send-email.js tiene doble export de onRequestPost

Problema: El archivo functions/send-email.js exporta onRequestPost dos veces (línea 253 redefine la de línea ~0 implícita). En ESM estricto, la segunda exportación sobrescribe la primera. El rate limiting y la sanitización están en la segunda función, pero si Cloudflare procesa esto de forma distinta, podría ejecutar la primera (sin protección).

Impacto: Confusión en mantenimiento, posible riesgo de ejecutar código sin sanitizar.

Solución: Unificar en un solo export — eliminar la primera declaración vacía implícita o reestructurar.

ALTO

H-03: mp-create-preference rate limit fail-open

Problema: En functions/mp-create-preference.js, el checkRateLimit retorna null si KV falla (línea 111: catch { return null; }), permitiendo bypass del rate limit. Todas las demás funciones ya fueron corregidas a fail-closed, pero esta quedó sin corregir.

Impacto: Un atacante puede hacer spam de preferencias de MercadoPago, generando costos en API y potencialmente abusando del sistema.

Solución: Cambiar la línea 106-107 a return 'Service temporarily unavailable'; como en las demás funciones.

Severidad Media
MEDIO

M-01: Monolito index.html de ~19.5K líneas

Problema: Todo el CSS, JS y HTML de la app está en un solo archivo de ~19.500 líneas. Esto impacta: tiempo de parseo en dispositivos baratos (~2-4s), imposibilidad de cacheo granular, dificultad de mantenimiento.

Impacto: Performance en celulares gama baja, DX de mantenimiento.

Solución: Para v2 considerar extraer CSS y JS a archivos separados. A corto plazo, el lazy-loading de CDN mitiga parcialmente.

MEDIO

M-02: SRI hashes son placeholder

Problema: Los hashes SRI en CDN_SRI fueron generados como placeholder (el entorno bloqueó la descarga de CDNs). Si los hashes no coinciden con los archivos reales, las cargas de Chart.js, jsPDF y XLSX fallarán silenciosamente.

Impacto: Estadísticas, exportación PDF y Excel podrían no cargar en producción.

Solución: Ejecutar localmente: curl -s URL | openssl dgst -sha384 -binary | base64 para cada CDN y reemplazar los hashes.

MEDIO

M-03: Sin mecanismo de unsubscribe en emails

Problema: Los emails transaccionales (trial_welcome, trial_reminder, trial_expired) no incluyen header List-Unsubscribe ni link de baja automático. Solo dicen "escribinos a parfumtrack@gmail.com". Esto viola RFC 8058 y puede causar problemas de deliverability con Gmail/Outlook.

Impacto: Riesgo de que emails caigan en spam, mala reputación de sender.

Solución: Agregar header List-Unsubscribe-Post y link de baja real, o al menos un endpoint que registre la preferencia.

MEDIO

M-04: Email templates usan links parfumtrack.pages.dev

Problema: En send-email.js, los CTAs de email apuntan a "parfumtrack.pages.dev" como fallback (línea 62, 75, 128, etc.). Si APP_URL no está configurada en env, los usuarios llegarán a una URL incorrecta.

Impacto: Usuarios que hacen click en emails llegan a URL muerta/incorrecta.

Solución: Cambiar todos los fallbacks de "parfumtrack.pages.dev" a "parfumtrack.luccasramireziglesias.workers.dev".

MEDIO

M-05: Trial sync tokens siguen retornándose

Problema: En trial.js línea 257, la respuesta de handleVerify aún incluye syncCode y syncToken. Aunque el frontend ya no los usa, siguen expuestos en la respuesta de red, lo que es superficie de ataque innecesaria.

Impacto: Exposición de material criptográfico potencialmente reutilizable.

Solución: Eliminar syncCode y syncToken de la respuesta JSON en trial.js.

MEDIO

M-06: validate-license rate limit fail-open

Problema: En validate-license.js línea 219-221, cuando KV falla en la lectura del rate limit, retorna null (fail-open). Inconsistente con las demás funciones que ya usan fail-closed.

Impacto: Brute-force de códigos de licencia si KV está caído.

Solución: Cambiar catch { return null; } a catch { return 'Rate limit check failed'; }

MEDIO

M-07: mp-subscription-status rate limit fail-open

Problema: En mp-subscription-status.js línea 86, catch { return null; } permite bypass del rate limit cuando KV falla.

Impacto: Enumeration de suscripciones sin limitación.

Solución: Cambiar a fail-closed como en las demás funciones.

MEDIO

M-08: Sin tests automatizados

Problema: No hay test suite. Ni tests unitarios para las funciones backend ni tests E2E para la app. Los cambios se validan solo visualmente.

Impacto: Riesgo de regresiones en cada deploy, especialmente con un monolito de 19K líneas.

Solución: Agregar tests para las funciones críticas: validate-license, mp-webhook, trial. Usar Vitest + wrangler miniflare.

Severidad Baja
BAJO

L-01: Floating cards wrapper solo se ve en mobile

El wrapper .hero-floating-cards-wrap necesita estar oculto en desktop para no romper el layout absolute de las cards. Verificar que el CSS desktop no muestra el wrapper como flex.

BAJO

L-02: wrangler.jsonc assets.directory = "."

Servir todo el directorio raíz como assets expone archivos no deseados (PLAYSTORE/, standalone/, .claude/). Considerar mover los assets a un subdirectorio /public.

BAJO

L-03: handleLegacy nunca se invoca

En trial.js, la función handleLegacy (líneas 262-298) está definida pero nunca se llama — el path legacy ahora retorna 410 en línea 57. Código muerto.

BAJO

L-04: No hay Content-Security-Policy header

No se configura CSP en el worker ni en las respuestas. Agregar un CSP header protegería contra inyección de scripts no autorizados.

BAJO

L-05: Falta alt text dinámico en catálogo canvas

El canvas del catálogo no tiene aria-label descriptivo. Usuarios de screen readers no pueden entender el contenido.

💼 Análisis de Negocio y Competencia

Propuesta de valor

Clara y enfocada: App para revendedores de perfumes en LATAM. El nicho está bien definido. La competencia genérica (Excel, cuaderno, apps contables) no entiende el workflow de cuotas + WhatsApp + stock de fragancias. Diferenciación sólida.

Monetización

Freemium viable: Free ilimitado → Básico Pro USD 9.99/mes. El precio es accesible para el target (ganan $30-100K/mes en Argentina). La fricción de pago está bien resuelta con MercadoPago + WhatsApp alternativo. Falta: plan anual con mayor descuento para reducir churn.

Riesgos principales

1) Dependencia de localStorage: Si un usuario pierde el celular, pierde todo. El backup en nube solo funciona con plan pago. 2) Mercado de nicho pequeño: Revendedores de perfumes es un segmento acotado. 3) Sin moat técnico: La app es replicable. El moat es la comunidad y el boca a boca.

Competidores

Directos: Ninguno específico para perfumes en LATAM. Indirectos: Excel, Google Sheets, apps genéricas de ventas (Alegra, Contabilium, Bind). Ventaja: ParfumTrack es 10x más simple y no requiere cuenta ni setup. Debilidad: Sin app nativa en stores (PWA only).

🧠 Ventas y Psicología

¿Qué impediría comprar?

1) "¿Y si pierdo mis datos?" — El miedo #1. La app guarda todo en localStorage. Falta messaging claro sobre backup y qué pasa si cambio de celular. 2) "No conozco a nadie que lo use" — Falta prueba social con nombres/fotos reales. 3) "¿Quién está detrás?" — No hay página de "quiénes somos". Falta humanizar la marca.

Fortalezas de conversión

1) 10 segundos para probar — Sin registro, sin descarga, sin tarjeta. Barrera de entrada casi cero. 2) Datos demo precargados — El usuario ve valor inmediato sin cargar nada. 3) Voseo argentino — Se siente cercano, no corporativo. 4) WhatsApp cobro integrado — Soluciona el dolor #1 (cobrar cuotas).

Oportunidades de mejora

1) Onboarding más guiado: El tour existe pero podría tener un "Registrá tu primera venta real" interactivo. 2) Micro-wins tempranos: Mostrar "ganaste $X hoy" después de la primera venta. 3) Reminder de valor: Push semanal con "Esta semana ganaste $X" mantiene engagement sin esfuerzo.

Funnel de conversión

Awareness: WhatsApp viral (catálogo + cobro firmados) + landing con SEO LATAM. Consideration: Datos demo + trial 14 días. Conversion: Paywall suave + MercadoPago. Punto débil: Awareness → la app no tiene forma orgánica de descubrimiento fuera de WhatsApp. Necesita contenido SEO (blog con "cómo ganar más vendiendo perfumes").

🪞 Autocrítica

¿Qué falta?

No pude testear la app en un navegador real. El análisis es puramente estático (lectura de código). No verifiqué: rendimiento real en dispositivos baratos, tiempos de carga, comportamiento offline real, ni interacción con MercadoPago en producción. Los SRI hashes necesitan validación empírica.

¿Qué asumí sin evidencia?

1) Que "+340 revendedores" es un número creíble (no verifiqué analytics reales). 2) Que el payment flow de MP funciona end-to-end (no tengo acceso al dashboard MP). 3) Que los emails de Brevo llegan correctamente (no tengo acceso al sender reputation). 4) Que el nicho de revendedores de perfumes en LATAM es lo suficientemente grande para ser viable.

¿Qué necesita más investigación?

1) Tamaño real del mercado (TAM de revendedores de perfumes en AR/UY/CO/MX). 2) Churn rate actual de los trial users. 3) Conversion rate trial → pago. 4) CAC real por canal. 5) Performance real en celulares gama baja (Motorola E, Samsung A03). 6) Service Worker caching behavior con updates.
