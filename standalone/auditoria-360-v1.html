ALTO ARQ-01: Monolito frontend de 6.189 líneas
Problema: Todo el frontend (CSS + HTML + JS) vive en un solo archivo. Impide code splitting, testing unitario, y trabajo en paralelo.
Impacto: Mantenibilidad baja. Cada cambio requiere parsear 6K+ líneas. No se puede hacer tree-shaking ni lazy loading de secciones.
Solución: Refactorizar a módulos ES: css/, components/, lib/ con un bundler mínimo (esbuild). Roadmap 90 días.
Score: 6/10
MEDIO ARQ-02: Sin build step ni bundler
Problema: No hay minificación, tree-shaking, ni source maps. El HTML se sirve tal cual.
Impacto: ~30% más peso del necesario. Sin source maps, debugging en prod es difícil.
Solución: Agregar esbuild como build step mínimo. Mantener DX simple.
Score: 7/10
OK ARQ-03: Backend bien segmentado
Detalle: 10 funciones Workers bien separadas por responsabilidad. Shared utilities en _shared.js. Router limpio en worker.js.
Score: 9/10

Fase 04 — ArquitecturaAuditoría Backend

RESUELTO BE-01: requireJson solo valida Content-Length header
Archivo: _shared.js
Fix: Se agregó parseJsonBody() que lee el body real con request.text() y valida text.length > maxBytes antes de parsear. Migrado en 7 endpoints.
MEDIO BE-02: Rate limit no es atómico
Archivo: _shared.js:19-39
Causa: checkRateLimit hace GET + PUT separados. Bajo carga concurrente, dos requests pueden leer el mismo count y ambas pasar.
Impacto: TOCTOU race condition. En la práctica es aceptable porque KV es eventually consistent y el volumen es bajo.
Fix: Aceptable para el volumen actual. Para escalar, usar Durable Objects con atomic counters.
OK BE-03: HMAC auth sólida en backup/sync
Token HMAC-SHA256 con timing-safe comparison. Validación de formato de código. Rate limiting por IP y por código. Score: 9/10
OK BE-04: Webhook MP con verificación de firma
Signature verification con timing-safe comparison, replay protection (5 min window), idempotencia via KV (processing → done). Score: 9/10

MEDIO DB-01: Fotos como data URI en IndexedDB

IndexedDB v3 sin plan de migración. Si se agregan stores nuevos o se cambian índices, necesita lógica de upgrade en onupgradeneeded. Actualmente funciona porque todos los stores se crean con if (!contains).

Fase 33 — EjecutivoResumen Ejecutivo

Estado general del producto
Parfum Track es una PWA funcional y bien ejecutada para un nicho ultra-específico (revendedores de perfumes en LATAM). El producto resuelve un problema real con una UX excepcional (time-to-value de 10 segundos). La arquitectura backend es sólida: auth HMAC/ECDSA, rate limiting fail-closed, idempotencia en webhooks, structured logging.

Fortalezas principales: Offline-first real, cobro por WhatsApp (único), sin registro, UX mobile-first, paleta visual premium.
Debilidades principales: Monolito frontend (6K líneas), sin tests frontend, monetización débil (Free demasiado generoso).
Mejoras completadas: 2 XSS corregidos, 209 tests backend, parseInt→parseFloat, PIN hasheado, prompt→modal, trial bug fix.
Oportunidad #1: Growth loops orgánicos vía WhatsApp (branding en mensajes de cobro).
