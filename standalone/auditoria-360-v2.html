ALTO ARQ-01: Monolito frontend de ~6.200 líneas
Problema: Todo el frontend vive en un solo archivo. Impide code splitting, testing unitario, y trabajo en paralelo.
Impacto: Mantenibilidad baja. No se puede hacer tree-shaking ni lazy loading de secciones.
Solución: Refactorizar a módulos ES con esbuild. Roadmap 90 días.
Score: 6/10
MEDIO ARQ-02: Sin build step ni bundler
Problema: No hay minificación, tree-shaking, ni source maps. El HTML se sirve tal cual.
Impacto: ~30% más peso del necesario. Sin source maps, debugging en prod es difícil.
Solución: Agregar esbuild como build step mínimo.
Score: 7/10
OK ARQ-03: Backend bien segmentado
Detalle: 10 funciones Workers bien separadas por responsabilidad. Shared utilities en _shared.js. Router limpio en worker.js.
Score: 9/10

Estado: RESUELTO en PR #48 — Se usa this.esc(mejorV[0]).
RESUELTO FE-03: parseInt trunca decimales en precios
Estado: RESUELTO en PR #48 — parseInt() reemplazado por parseFloat().
RESUELTO FE-04: Redondeo de cuotas pierde dinero
Fix: Última cuota ajustada con montoTotal - (montoCuota * (n-1)) (PR #48).
RESUELTO FE-05: Método duplicado marcarPagada
Fix: Duplicación eliminada (PR #48).
RESUELTO FE-06: togglePin usa prompt() nativo
Fix: Reemplazado por modal custom con appPrompt() (PR #48).
RESUELTO FE-07: user-scalable=no en viewport
Estado: RESUELTO en PR #48 — Removido, agregado touch-action: manipulation.
RESUELTO FE-08: Primera cuota marcada pagada sin monto
Fix: Agregado montoPagado: i === 0 ? montoCuota : 0 (PR #48).
RESUELTO v2 FE-09: 16 operaciones DB sin try-catch
Problema: guardarVenta, guardarPedido, guardarCaja, guardarGasto, addPerfume, deleteVenta, deletePedido, deleteCaja, deleteGasto, updateVenta, updatePedido, marcarPedidoEnviado, marcarPedidoPendiente, adjustStock, photo update, confirmarPagoCuota — todas sin manejo de errores.
Impacto: Un error de IndexedDB (QuotaExceeded, disco lleno, etc.) hacía crash silencioso. El usuario no sabía si sus datos se guardaron.
Fix: Las 16 operaciones envueltas en try-catch con toast informativo al usuario.
RESUELTO v2 FE-10: Import/restore sin tracking de fallos
Problema: _restoreData() tenía catch {} silencioso. Si un item fallaba al importar, el usuario no lo sabía.
Fix: Se agregó contador skipped. Return cambiado a { total, skipped }. Toast muestra "X registros importados (Y omitidos)".

Fase 04 — ArquitecturaAuditoría Backend

RESUELTO BE-01: requireJson solo valida Content-Length header
Fix: Se agregó parseJsonBody() que valida tamaño real del body. Migrado en 7 endpoints.
MEDIO BE-02: Rate limit no es atómico
Causa: TOCTOU race condition en GET+PUT de KV. Aceptable para volumen actual.
Fix: Para escalar, usar Durable Objects con atomic counters.
OK BE-03: HMAC auth sólida en backup/sync
Token HMAC-SHA256 con timing-safe comparison. Score: 9/10
OK BE-04: Webhook MP con verificación de firma
Signature verification con timing-safe comparison, replay protection, idempotencia. Score: 9/10
RESUELTO v2 BE-05: NaN bypass en checkRateLimit
Archivo: _shared.js:29
Problema: parseInt(stored, 10) con KV corrupto retorna NaN. NaN >= max es false → bypass total del rate limit.
Fix: parseInt(stored, 10) || 0 — NaN se convierte a 0.
RESUELTO v2 BE-06: KV put sin try-catch en validate-license
Archivo: validate-license.js:103
Problema: env.PT_LICENSES.put() sin protección. Error de KV → 500 sin mensaje descriptivo.
Fix: Try-catch con log de error y respuesta { ok: false, error: 'Storage error' }.
RESUELTO v2 BE-07: KV get sin try-catch en mp-subscription-status
Archivo: mp-subscription-status.js:39
Fix: Try-catch alrededor de env.PT_LICENSES.get() con respuesta 500 descriptiva.
RESUELTO v2 BE-08: KV reads sin try-catch en mp-payment-status
Archivo: mp-payment-status.js:60-70
Fix: Try-catch con log de error estructurado alrededor de ambos KV.get().

Fase 33 — EjecutivoResumen Ejecutivo

Estado general del producto — v2
Parfum Track es una PWA funcional y robusta para revendedores de perfumes en LATAM. Time-to-value de 10 segundos. Backend con auth HMAC/ECDSA, rate limiting fail-closed, idempotencia en webhooks, structured logging, y error handling completo en 100% de las operaciones KV.

Mejoras v1 (PR #48-49): 2 XSS corregidos, 209 tests, parseInt→parseFloat, PIN hasheado, prompt→modal, trial bug fix.

Total: 31 bugs corregidos en 2 sesiones. 0 bugs críticos activos.
Debilidades restantes: Monolito frontend (requiere refactor 2-4 semanas), CSP unsafe-inline (depende de modularización), monetización débil.
