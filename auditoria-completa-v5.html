Fase 1 — Comprensión

Qué hace

Gestión de ventas para revendedores de perfumes: registrar ventas, controlar stock, gestionar cuotas/cobros, estadísticas, catálogo por WhatsApp. Funciona 100% offline.

Problema que resuelve

Revendedores usan cuadernos/Excel y pierden control de ganancias, cobros pendientes y stock. ParfumTrack automatiza eso en 10 segundos por venta.

Usuario objetivo

Revendedores de perfumes en Argentina, Uruguay, Colombia y México. Emprendedores móviles, mayormente celular.

Propuesta de valor

Gratis para siempre, funciona offline, diseñada específicamente para perfumes, sin cuenta ni contraseña.

Fase 2 — Auditoría Técnica

Seguridad

Crítico
1. Licencia bypasseable desde consola

Problema: _sec.activate(new Uint8Array(64)) desde la consola activa el plan Pro. Solo verifica instanceof y length, no la firma criptográfica real. La verificación ECDSA solo corre al startup.

Impacto: Cualquier usuario técnico accede a todas las funciones pagas sin pagar.

Solución: Verificar la firma ECDSA dentro de activate(), no solo en initLicenseVerification().

Crítico
2. Webhook MP: pago silenciosamente perdido si KV falla

Problema: mp-webhook.js línea 72 retorna {ok: true} (200) cuando PT_LICENSES KV no está disponible. MercadoPago no reintentará.

Impacto: El usuario paga pero nunca recibe su licencia. Dinero cobrado, servicio no entregado.

Solución: Retornar HTTP 500 para que MP reintente. Implementar dead letter queue.

Crítico
3. Push notifications sin autenticación

Problema: send-notification.js permite enviar push a cualquier subscription ID sin credenciales. Auth es "recomendado, no requerido aun".

Impacto: Cualquiera puede enviar spam/phishing push a los usuarios de la app.

Solución: Hacer auth obligatorio. Fallar cerrado cuando no hay credenciales.

Crítico
4. Webhook idempotency race condition

Problema: mp-webhook.js check 'done' → write 'processing' no es atómico. KV eventual consistency permite que dos webhooks procesen el mismo pago, duplicando la licencia o extendiendo el período.

Impacto: Doble procesamiento de pagos, licencias duplicadas.

Solución: Usar KV con metadata y compare-and-swap, o Durable Objects para lock distribuido.

Alto
5. CSP permite unsafe-inline

Problema: _headers CSP incluye 'unsafe-inline' para script-src y style-src. Con 86 innerHTML y 202 onclick inline, cualquier XSS tiene ejecución libre.

Solución: Migrar a event listeners y nonce-based inline scripts progresivamente.

Alto
6. mp-payment-status sin rate limiting ni auth

Problema: Cualquier cliente puede enumerar payment IDs y ver el estado de licencias de otros usuarios.

Solución: Agregar rate limiting y requerir token HMAC del usuario.

Alto
7. Assets directory "." puede servir archivos sensibles

Problema: wrangler.jsonc assets.directory es "." — podría servir wrangler.jsonc, worker.js y archivos de configuración como assets estáticos.

Solución: Mover assets a un subdirectorio /public y actualizar la config.

Medio
8. Data loss silencioso en migración

Problema: Línea 6653 catch(e){} vacío en migración localStorage→IndexedDB. Si JSON.parse falla, los datos se pierden sin aviso.

Solución: Loguear error y mostrar toast de advertencia al usuario.

Medio
9. Backup token en URL query string

Problema: /backup?code=X&token=Y expone credenciales en logs de servidor e historial del navegador.

Solución: Enviar código y token en el body del POST o en headers.

Medio
10. sync.js no normaliza código a uppercase

Problema: sync POST no hace .toUpperCase() en el código vs backup.js que sí lo hace. Puede causar claves R2 duplicadas.

Solución: Agregar code = code.toUpperCase() en sync.js POST handler.

Código y Arquitectura

Alto
11. Monolito de 19K líneas en un solo archivo

Todo el CSS, HTML y JS están en index.html. Hace imposible el mantenimiento, testing, code review y colaboración. Sin bundler, sin módulos, sin componentes.

Medio
12. Duplicación masiva de patrones

Lógica de pago de cuotas duplicada en 3 funciones. Estilos de input inline repetidos 8+ veces. Temas de catálogo definidos en 2 lugares. Text-wrapping implementado 2 veces.

Medio
13. Bug: comparación de fechas por string

Línea 7961 usa comparación string en formato DD/MM/YYYY para ordenar clientes. "02/01/2026" > "31/12/2025" es false por comparación alfabética. Produce ordenamiento incorrecto.

Medio
14. Bug: ganancia pierde descuento al editar venta

addVenta aplica descuento en cálculo de ganancia. guardarEditarVenta no lo aplica. Editar una venta con descuento altera la ganancia sin que el usuario lo sepa.

Bajo
15. Mutex por setTimeout de 800ms

_addingStock usa boolean + setTimeout como guard contra doble-submit. Si save() tarda más de 800ms, el guard ya se liberó.

Frontend / UX / UI

Medio
16. Accesibilidad insuficiente

Solo 79 ARIA attrs en 19K líneas. Zero labels con for=. Botones onclick en divs sin role="button". PIN pad sin aria-labels. Links legales son spans sin tabindex.

Bajo
17. Modales sin focus trap

Aunque tienen aria-modal="true", el tab key puede navegar a elementos detrás del modal overlay.

Bajo
18. No hay noscript fallback en landing

FAQ, animaciones reveal y toggle de pricing dependen de JS. Sin JS, FAQs cerrados permanentemente y secciones invisibles.

Fase 4 — Startup y Negocio

Propuesta de valor

Fuerte: gratis, offline, sin cuenta, diseñada para perfumes. Diferenciación real vs Excel/cuadernos.

Mercado

Nicho específico (revendedores de perfumes LATAM). Mercado fragmentado, sin competidor dominante en el nicho.

Monetización

Freemium con Free permanente. Conversión depende de valor percibido del Pro. El free ilimitado es excelente para distribución orgánica pero arriesga conversión baja.

¿Por qué podría fracasar?

  • El plan Free es tan completo que nadie pague
  • No hay onboarding guiado — usuario abandona sin entender el valor
  • Sin métricas de usuario, no sabés qué funciona
  • Dependencia de un solo desarrollador (bus factor = 1)
  • La licencia es bypasseable — los usuarios técnicos no pagarán

Fase 5 — Ventas y Psicología

Landing: lo que funciona

  • Copy excelente — usa voseo argentino, pain points específicos
  • Múltiples CTAs bien distribuidos (announce bar, nav, hero, features, pricing, final)
  • Trust signals: "+340 revendedores", badges de funciones, trust bar
  • Screenshots reales de la app en vez de mockups (recién agregados)
  • FAQ bien pensado con objeciones reales

Lo que falta / frena

  • "+340 revendedores" — si es inventado, destruye confianza al descubrirse
  • Sin video demo — el usuario no ve la app en acción
  • Sin urgencia ni escasez — no hay razón para actuar HOY
  • Testimonios eliminados (correcto si eran falsos) pero no hay social proof real
  • Pricing sin trial del Pro — el usuario no puede probar antes de pagar
