V5-01 XSS almacenado en renderGastos() — fallback de categoría sin escapar Corregido
Severidad
Alto
Impacto
Un atacante que logre insertar una categoría de gasto con payload XSS (vía manipulación de IndexedDB, importación de backup o explotación de otro vector) obtiene ejecución de código en contexto de la app.
Causa
getAllCatLabels()[cat] || cat — si la clave no existe en el mapa de labels, el valor raw se renderiza directamente en innerHTML sin escapar.
Ubicación
renderGastos() — dos puntos de inyección: el <span> de categoría en la fila y el título del detalle modal.
Solución
Reemplazar el fallback raw con escapeHTML(cat) y escapeHTML(g.categoria) en ambos puntos de render.
// ANTES (vulnerable)
html += `<span>${getAllCatLabels()[cat] || cat}</span>`;

// DESPUÉS (seguro)
html += `<span>${getAllCatLabels()[cat] || escapeHTML(cat)}</span>`;

// ANTES (modal, vulnerable)
const titulo = g.categoria === "otro" && g.nombreOtro
  ? `📋 ${g.nombreOtro}`
  : getAllCatLabels()[g.categoria] || g.categoria;

// DESPUÉS (modal, seguro)
const titulo = g.categoria === "otro" && g.nombreOtro
  ? `📋 ${escapeHTML(g.nombreOtro)}`
  : getAllCatLabels()[g.categoria] || escapeHTML(g.categoria);

V5-02 DoS por archivo de backup sin límite de tamaño Corregido
Severidad
Alto
Impacto
Un usuario malicioso (o un archivo corrompido) puede subir un JSON de varios GB. FileReader intenta cargar el blob completo en memoria, lo que congela y en muchos casos crashea la pestaña del navegador — pérdida de datos del usuario final.
Causa
restoreBackup() llamaba directamente a FileReader.readAsText() sin verificar file.size.
Cómo reproducir
Crear un archivo JSON de 50 MB (e.g. con dd if=/dev/urandom bs=50M count=1 | base64 > huge.json) y arrastrarlo al input de restore.
Solución
Verificar file.size antes de invocar FileReader. Límite: 5 MB (suficiente para miles de ventas).
function restoreBackup(e) {
  const file = e.target.files[0];
  if (!file) return;
  // ← NUEVO: guardia de tamaño
  if (file.size > 5 * 1024 * 1024) {
    toast("⚠ El archivo es demasiado grande (máx. 5 MB)", 4000);
    e.target.value = "";
    return;
  }
  const r = new FileReader();
  // ...
}

V5-03 DoS por arrays masivos en backup (sin cota superior) Corregido
Severidad
Medio
Impacto
Un JSON técnicamente < 5 MB pero con 100 000 ventas vacías (o un solo campo enorme repetido) pasa el límite de tamaño pero luego provoca iteración excesiva en la restauración y en los renders posteriores, bloqueando el hilo principal.
Causa
_validarSchemaBackup() solo validaba estructura de los primeros 50 ítems, pero no acotaba el total de elementos en el array.
Solución
Rechazar backups con arrays que superen los límites operativos esperados (ventas: 50 000, perfumes: 10 000, gastos: 20 000).
// Añadido en _validarSchemaBackup():
if (Array.isArray(data.ventas) && data.ventas.length > 50000)
  return "⚠ El backup tiene demasiadas ventas — archivo sospechoso.";
if (Array.isArray(data.perfumes) && data.perfumes.length > 10000)
  return "⚠ El backup tiene demasiados perfumes — archivo sospechoso.";
if (Array.isArray(data.gastos) && data.gastos.length > 20000)
  return "⚠ El backup tiene demasiados gastos — archivo sospechoso.";

V5-04 Validación de longitud en addGasto() — monto y campos de texto Corregido
Severidad
Medio
Impacto
Sin cota en el monto, un valor como 1e308 se almacena como Infinity, corrompiendo los totales. Sin cota en descripción/nombreOtro, un texto de 10 MB infla IndexedDB y eventualmente rompe la exportación de backup.
Solución
Validación en el punto de entrada: monto ≤ 10 000 000, descripción ≤ 500 chars, nombreOtro ≤ 100 chars.
// Añadido en addGasto():
if (monto > 10_000_000) {
  toast("⚠ El monto parece muy alto. Verificá los datos");
  return;
}
if (desc.length > 500) {
  toast("⚠ La descripción es demasiado larga (máx. 500 caracteres)");
  return;
}
if (otroNombre.length > 100) {
  toast("⚠ El nombre del gasto es demasiado largo (máx. 100 caracteres)");
  return;
}

⚠️ Riesgos residuales y aceptaciones
RR-01 unsafe-inline en script-src / style-src — CSP parcialmente permisivo Aceptado
Severidad
Medio
Motivo aceptación
La app es una SPA monolítica con todo el JS/CSS inline. Migrar a nonces requeriría un servidor dinámico y una refactorización mayor — fuera del scope actual.
Mitigación activa
COOP + CORP + X-Frame-Options DENY + no eval — reduce el riesgo de explotación si existiera un XSS desconocido.
Riesgo real
Bajo — todos los inputs de usuario ya pasan por escapeHTML(); la superficie XSS primaria está cerrada.
RR-02 Datos almacenados en IndexedDB sin cifrado Aceptado
Severidad
Medio
Motivo aceptación
Cifrado client-side en IndexedDB requiere gestión de claves de usuario — complejidad alta con potencial de pérdida de datos si el usuario olvida su clave. El modelo de amenaza principal (resellers individuales) no justifica el overhead.
Mitigación activa
PIN de 6 dígitos con sal aleatoria por dispositivo (_ensurePinSalt()), HTTPS obligatorio (HSTS), COOP/CORP limita acceso entre origins.
Riesgo real
Bajo-Medio — requiere acceso físico al dispositivo o un XSS (ya mitigado) para acceder a los datos.
RR-03 Subrecursos externos (OneSignal, Google Fonts, Cloudflare) sin SRI Bajo riesgo
Severidad
Bajo
Contexto
Los CDN en uso (OneSignal, cdnjs.cloudflare.com, Google Fonts) tienen SLA de integridad y son ampliamente monitoreados. SRI bloquearía actualizaciones automáticas de estos proveedores.
Mitigación activa
CSP allowlist explícita limita el origen de los scripts — un CDN comprometido fuera de la lista sería bloqueado.
